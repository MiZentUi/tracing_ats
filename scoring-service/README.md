# scoring-service

Python 3.14, uv, gRPC, Pydantic. Онлайн-ML: разбор обезличенного резюме через LLM и расчёт математической модели.

Сервис stateless: не читает файлы, не ходит в PostgreSQL, MinIO, hh, GitHub и не получает PII. LLM вызывается только с обезличенным текстом.

## Текущее состояние

`ScoringService.ScoreResume` вызывает LLM для извлечения признаков из
обезличенного резюме: навыков, образования и опыта. Ответ модели — строгий JSON
по схеме `ParsedResume`; каждая цитата проверяется как подстрока текста (пробелы
схлопываются, offsets считаются по исходному тексту). Признаки без валидной
цитаты отбрасываются.

`ScoringService.ExtractResume` — отдельный метод без вакансии: он вызывает тот же
экстрактор и возвращает `ParsedResume` (`schema_version`, `skills`, `education`,
`experience`) и `dropped` — число признаков, отброшенных из-за невалидной
цитаты. Скоринг в этом методе не считается.

`S^{ij}` считается детерминированно в `src/api/scoring/similarity.py`:

- имена навыков, направлений и категорий опыта нормализуются; точное совпадение
  даёт `1.0`, вхождение токенов или близость `SequenceMatcher >= 0.8` — `0.85`,
  близость `>= 0.7` — `0.5`, иначе `0.0`;
- для образования сходство направления даёт 70%, соответствие уровня — 30%;
- для текстовых требований `S` — доля значимых токенов требования, найденных
  в тексте резюме.

`R_i` — лучшее сходство по проверенным признакам резюме. `t_i` для навыков
выводится из цитаты секционными правилами: результат или метрика — `0.8`,
обязанность — `0.5`, остальное — `0.3`. `τ_i` — произведение фактора стажа
`0.5·(1+tanh(years/required − 1))` и свежести `2^(−recency/2)`; неизвестные
стаж и давность расширяют вилку, а не обнуляют требование. `c_i` для навыка —
`S·t·τ`, для опыта — `S·τ`, для образования и текста — `S`.

`Wv^i` пока выводится из критичности: `OPTIONAL 0.25`, `NICE 0.5`,
`REQUIRED 0.75`, `CRITICAL 1.0`, `UNSPECIFIED 0.5`. `Score` — взвешенное
покрытие `Σ Wv^i c_i / Σ Wv^i`. Для известных признаков `Score_l`/`Score_h`
получаются подстановкой граничных `τ`, для `NOT_STATED` верхняя граница — `1.0`.
Внешних источников в контракте нет, поэтому `λ = 0`; `F = 0`, `𝓜 = 1`, пока
формула домена не зафиксирована. Пороги статусов зависят
от типа требования: `0.85`/`0.5` для структурированных признаков, `0.75`/`0.35`
для текстовых. Если признак или проверенная цитата не найдены, ставится
`NOT_STATED` — «в резюме нет сведений», а не «навыка нет».

Значения `S`, `t`, `Wv` и `F` остаются открытыми вопросами
`docs/rfc/rfc-scoring-model.md`; реализация вынесена в заменяемые политики,
поэтому их фиксация не требует правок сопоставления и арифметики.

Провайдер по умолчанию — `mock`: детерминированная заглушка без сети и ключей,
нужная для CI и демо. Реальный OpenAI-совместимый провайдер включается
`SCORING_SERVICE_LLM_PROVIDER=openai`.

## Детерминированные объяснения

`src/api/scoring/feedback.py` собирает `strengths`, `risks`, `questions` и
`recruiter_note` по уже посчитанным `RequirementScore`. LLM для этого не
вызывается: `EvaluateResumeMatch` и `EvaluateResumeMatches` остаются
детерминированными.

- Каталог `feedback-templates.v1` содержит 30 шаблонов: 5 сильных сторон,
  8 рисков, 9 вопросов, 6 элементов рекомендации и 2 fallback.
- Факты выбираются по статусу, `gap_reason`, критичности, стажу, цитате и
  датам; шаблон только формулирует факт.
- Вариант шаблона выбирается стабильным хешем `fact_id`, поэтому один и тот же
  вход даёт один и тот же текст.
- `NOT_STATED` формулируется как «в резюме не указано», а не «нет навыка»;
  `ABSENT` — как «есть близкий опыт, но требование не подтверждено».
- Цитата в сильной стороне берётся только из проверенного `match.evidence`.
- `gaps` не меняются и остаются структурированными; отдельного `weaknesses`
  в v1 нет.
- Лимиты: 5 сильных сторон, 5 рисков, 5 вопросов, 500 символов на
  `recruiter_note`. Приоритеты и лимиты — политика отображения, не формула
  скоринга.

Правила и полный каталог зафиксированы в
`docs/rfc/rfc-feedback-generation.md`. В лог пишутся только количества и версия
каталога, без текстов резюме и цитат.

## LLM

- Промпт и JSON-схема лежат в `src/api/prompts/resume_extraction.py`, версия
  промпта — `resume-extraction.v1`.
- Клиент — `src/api/llm/client.py` на официальном SDK `openai`. `base_url`
  настраивается, поэтому подходит OpenRouter и локальные OpenAI-совместимые
  серверы. Повторы на 429/5xx и сетевые ошибки делает SDK (`max_retries`);
  один повтор на невалидный JSON/схему — на уровне экстрактора, затем ошибка,
  а не «0 баллов».
- В LLM уходит только обезличенный текст резюме. Тексты, цитаты и ответы модели
  не логируются; логируются только метаданные вызова: задержка, статус,
  `request_id`, токены и `finish_reason`.
- Ошибки: `INVALID_ARGUMENT` — пустой текст, `UNAVAILABLE` — LLM недоступна,
  `INTERNAL` — ответ не прошёл схему после повтора.

## Логирование

- gRPC-интерсептор `src/api/interceptors.py` пишет `grpc request start` и
  `grpc request end` с полным именем метода, статусом и `elapsed_ms`.
- Тела запросов и ответов не логируются: в них может быть текст резюме.
  При ошибке пишется класс исключения, но не его сообщение.

## Требования

- Python 3.14
- uv 0.13+

## Локальный запуск

```bash
uv sync
uv run scoring-service
```

Сервис слушает `0.0.0.0:8082`. Проверка здоровья:

```bash
uv run scoring-service-healthcheck
```

## Генерация gRPC

Сгенерированные protobuf/gRPC-модули лежат в `src/scoring_service/` и коммитятся вместе с контрактом. После изменения `.proto`:

```bash
uv run sh protoc.sh
```

## Конфигурация

Настройки читаются из переменных окружения с префиксом `SCORING_SERVICE_`.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `SCORING_SERVICE_GRPC_HOST` | `0.0.0.0` | Адрес gRPC-сервера |
| `SCORING_SERVICE_GRPC_PORT` | `8082` | Порт gRPC-сервера |
| `SCORING_SERVICE_LOG_LEVEL` | `INFO` | Уровень логирования |
| `SCORING_SERVICE_MAX_WORKERS` | `10` | Размер пула обработчиков gRPC |
| `SCORING_SERVICE_LLM_PROVIDER` | `mock` | `mock` или `openai` |
| `SCORING_SERVICE_LLM_BASE_URL` | — | База OpenAI-совместимого API; обязательна для `openai` |
| `SCORING_SERVICE_LLM_API_KEY` | — | Ключ провайдера; не логируется |
| `SCORING_SERVICE_LLM_MODEL` | — | Модель; обязательна для `openai` |
| `SCORING_SERVICE_LLM_TIMEOUT_SECONDS` | `30` | Таймаут одного запроса |
| `SCORING_SERVICE_LLM_MAX_RETRIES` | `1` | Повторы на 429/5xx и сеть |

Локальные значения можно положить в `scoring-service/.env`; файл не коммитится.

## Проверки

```bash
uv run pytest
uv run ruff check .
uv run ruff format --check .
```

CI выполняет эти же проверки в job `Python / scoring-service`, а также перегенерирует protobuf-модули через `protoc.sh` и проверяет, что они совпадают с закоммиченными.

## Docker

Из корня репозитория:

```bash
docker compose up --build scoring-service
```

Порт публикуется через `SCORING_SERVICE_PORT` (по умолчанию `8082`). Образ собирается на `python:3.14-slim`, зависимости ставятся из `uv.lock` через `uv sync --locked`.

## Структура

```text
scoring-service/
├── pyproject.toml
├── uv.lock
├── Dockerfile
├── src/api/
│   ├── config.py             # настройки из окружения
│   ├── server.py             # gRPC-сервер, health и ScoringService
│   ├── extraction/           # схема, нормализация и валидация цитат
│   ├── llm/                  # OpenAI-совместимый клиент и mock
│   ├── prompts/              # промпты и JSON-схема ответа
│   ├── scoring/              # gRPC-сервис, сопоставление, формулы и объяснения
│   └── healthcheck.py        # проверка для Docker/Compose
├── src/scoring_service/v1/   # сгенерированные protobuf/gRPC-модули
└── tests/
```

Вся арифметика живёт в `src/api/scoring/`: `similarity.py` — сходство,
`matcher.py` — `R_i`, `c_i` и статусы, `policies.py` — `Wv`, `τ`, `t` и `F`,
`calculator.py` — агрегаты и границы, `feedback.py` — объяснения. Формулы не
дублируются в Java и других сервисах.
