# Быстрое ревью в Tracing ATS

Цель — за ограниченное время найти то, что действительно ломает проект, а не переписать
код за автором. Сначала инварианты и контракты, потом корректность, потом стиль.

## 0. Собери diff

Сначала посмотри границы изменения, не весь репозиторий:

```bash
git diff --stat <base>...HEAD
git diff --check <base>...HEAD
git log --oneline <base>..HEAD
```

Читай целиком только изменённые функции и их ближайший контекст. Если файл изменён
больше чем наполовину — читай файл целиком.

## 1. Определи масштаб

Сначала ответь на три вопроса:

1. Какие сервисы и контракты затронуты: `backend`, `resume-service`, `vacancy-service`,
   `migrations`, `infra`, `contracts`, `scoring-service`, `ml-trainer`, `frontend`?
2. Меняются ли формула, константы, веса, схема БД или публичный/gRPC-контракт?
3. Есть ли в diff PII, секреты, новые внешние вызовы или новые зависимости?

Если затронуты формула, константа, контракт или приватность — это глубокое ревью.
Остальное можно пройти быстрым маршрутом.

## 2. Быстрый маршрут

Для небольшого diff без контрактов и скоринга проверь только это:

- [ ] Изменение делает то, что заявлено в описании, и не тащит посторонний рефакторинг.
- [ ] Нет PII, токенов, реальных резюме и секретов в коде, тестах, логах и фикстурах.
- [ ] Ошибки внешних вызовов обрабатываются: таймаут, повтор, деградация.
- [ ] Есть тест на новое поведение или объяснение, почему его нет.
- [ ] `Score_pre` и `Score_final` не смешаны; подписи в UI однозначны.
- [ ] Коммит соответствует Conventional Commits и содержит одно изменение.

## 3. Глубокий маршрут

Дополнительно проверь инварианты из `AGENTS.md` §4 и границы из §5.

### Скоринг и LLM

- [ ] LLM не выставляет баллов, процентов и чисел уверенности. Только категории `m`/`t`,
      цитаты и текст.
- [ ] Цитата проверяется как подстрока обезличенного текста. Непроверенная цитата
      отбрасывается, покрытие не завышается.
- [ ] Вся арифметика `q`, `E`, `D`, `c_r`, `M`, `N`, `F`, `Score`, cap, вилка и `refine`
      остаётся в `backend/scoring-service/app/scoring/` и не дублируется в Java, SQL или TypeScript.
- [ ] Константы (0.3/0.5/0.8, `T½`, `L_ref`, 0.70/0.15/0.15, порог cap 0.2) не менялись
      без ADR и обновления golden-тестов.
- [ ] `refine` не вызывает LLM повторно.
- [ ] Отсутствие GitHub не уменьшает балл; `external_skipped` — честное состояние.
- [ ] `Y_эфф` считается объединением периодов без двойного учёта.
- [ ] Новый `scoring_version` при изменении формулы; старые запуски не пересчитываются.

### Приватность и данные

- [ ] PII маскируется в Java до вызова LLM и до передачи в Python.
- [ ] `scoring-service` остаётся stateless: нет файлов, PostgreSQL, MinIO, hh, GitHub, токенов и PII.
- [ ] `ml-trainer` не ходит в БД, hh, GitHub и LLM; только тренировочный бакет MinIO.
- [ ] В логах только идентификаторы и технические метаданные, без текстов резюме и контактов.
- [ ] Тестовые данные синтетические.
- [ ] В исходящем запросе к LLM нет имён, контактов, пола, возраста, фото и вуза.

### Контракты и границы

- [ ] Код соответствует `backend/openapi.yaml`, `contracts/ml-internal.proto`,
      `contracts/training-artifact.schema.json`.
- [ ] Если контракт менялся, спецификация обновлена в том же изменении.
- [ ] Java не считает `q`, `E`, `D`, `c_r`, `M`, `N`, `F`, `Score`.
- [ ] Политика шорт-листа и решение «кого обогащать» остаются в Java, не в модели.
- [ ] GitHub вызывается только для шорт-листа и при согласии кандидата.
- [ ] Слепой режим: PII не попадает в ответ и DOM до `reveal`; раскрытие пишется в аудит.

### Миграции и инфраструктура

- [ ] Схема меняется только через Liquibase-миграции, а не через приложение и не руками.
- [ ] Миграции лежат в `backend/migrations` и накатываются джобой `migrations` из
      `infra/docker-compose.yml`, а не стартом сервисов.
- [ ] Новые changesets идут после существующих; старые не переписываются.
- [ ] У новых changesets есть `--rollback` или объяснение, почему его нет.
- [ ] `docker compose -f infra/docker-compose.yml config` остаётся валидным.

## 4. Запусти проверки

Не верь описанию изменения на слово. Минимальный набор:

```bash
# Java
mvn -f backend/pom.xml test

# миграции
docker compose -f infra/docker-compose.yml config
docker compose -f infra/docker-compose.yml run --rm migrations

# Python, когда появится
# pytest backend/scoring-service && pytest ml-trainer

# быстрый поиск опасных мест
rg -n "password|secret|token|BEGIN PRIVATE KEY" <затронутые файлы>
```

Если проверку нельзя запустить, прямо напиши, что именно не проверено и почему.

## 5. Формат ответа

Сначала вердикт одной строкой, затем замечания по убыванию важности.

```markdown
**Вердикт:** request changes — нарушен инвариант проверки цитат.

**BLOCKER**
- `backend/scoring-service/app/analyze/quote.py:42` — цитата принимается без проверки подстроки.
  Требование получает покрытие без доказательства. Проверять `quote in masked_text`
  до расчёта `c_r`.

**MAJOR**
- `backend/.../ScoreService.java:88` — балл считается в Java. Арифметика должна
  остаться в `backend/scoring-service/app/scoring/`.
- `backend/migrations/changes/002-...sql` — нет `--rollback`.

**MINOR / NIT**
- `...` — опечатка в имени поля.

**Что проверено**
- `mvn -f backend/pom.xml test` — зелёный.
- `docker compose ... config` — валиден.

**Не проверено**
- Реальный вызов LLM: нет ключа в окружении.

**Вопросы**
- Нужно ли сохранять старую версию профиля весов после активации?
```

## 6. Правила ревьюера

- Не выдумывай проблемы. Если сомневаешься — сформулируй один конкретный вопрос.
- Ссылайся на файл и строку, а не на «где-то в коде».
- Не предлагай переписать соседний код «заодно».
- Отделяй блокирующее от вкусового: `BLOCKER` / `MAJOR` / `MINOR` / `NIT`.
- Нарушения инвариантов из `AGENTS.md` §4 всегда выше остальных замечаний.
- Если изменение противоречит `README.md` или контракту, скажи об этом прямо.
- Не пиши «выглядит хорошо», если не запускал проверки. Перечисли, что реально проверено.
