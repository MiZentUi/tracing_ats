# Распределение задач: Java (`ats-service`) и Python (`scoring-service`)

> [!NOTE]
> Исторический план распределения задач. Эскиз контракта ниже не совпадает с
> фактическим `contracts/proto/scoring_service/v1/scoring.proto`
> (`ExtractResume`, `EvaluateResumeMatch`, `EvaluateResumeMatches`, `ScoreResume`).
> Актуальный контракт — proto, текущее состояние — `scoring-service/README.md`.

Цель: чтобы обе стороны могли работать изолированно. Для этого нужен общий **контракт** (описание данных, которые ходят между сервисами). Его делаем один раз вместе, дальше каждая сторона живёт отдельно. Java разрабатывается против заглушки Python-сервиса.

## Шаг 0. Общий для обоих (примерно полдня)

**Что делаем:** добавляем в proto два новых вызова к `scoring-service`.

- `ParseResume`: «прочитай резюме и верни структурированный профиль» (места работы, даты, образование, навыки).
- `EvaluateMatch`: «сравни профиль с одной вакансией и верни результат по каждому требованию».

Эскиз контракта:

```proto
rpc ParseResume(ParseResumeRequest) returns (ParseResumeResponse);
rpc EvaluateMatch(EvaluateMatchRequest) returns (EvaluateMatchResponse);

message ParseResumeRequest  { string masked_text = 1; string reference_date = 2; }
message ParseResumeResponse { string profile_json = 1; repeated string warnings = 2; }

message EvaluateMatchRequest {
  string profile_json = 1;
  string masked_text = 2;          // для проверки цитат
  Vacancy vacancy = 3;             // требования: id, text, category, kind, years_required, source
  string reference_date = 4;       // «сегодня», нужна для стажа
}

message EvaluateMatchResponse {
  double score = 1; double score_low = 2; double score_high = 3;
  repeated RequirementResult results = 4;
  repeated string strengths = 5; repeated string gaps = 6;
  repeated string risks = 7;     repeated string questions = 8;
  string recruiter_note = 9;
}

message RequirementResult {
  string requirement_id = 1;
  Status status = 2;               // FULL / PARTIAL / NONE / NOT_STATED
  string evidence_quote = 3;       // цитата из резюме, пусто если нет
  string comment = 4;
  double years_found = 5;
}
```

Затем Python-заглушка начинает отвечать **реалистичными фиксированными данными** (все четыре статуса, цитаты, вопросы). После этого Java строит всё остальное, не дожидаясь настоящей логики. Старый `ScoreResume` не трогаем.

## Java-сервис (`ats-service`)

Работает против заглушки.

### J1. Вакансии не только про IT
*Простыми словами:* сейчас система вытаскивает из вакансии «навыки» вроде Java и Spring. Для вакансий про учёт ОС или куратора нужны ещё «образование», «стаж 3+ года», «коммуникабельность». Учим систему различать тип требования (`category`) и откуда оно взято: из раздела «Требования» или выведено из «Обязанностей» (`source`).

- Миграция `016`, промпт v3, обновлённый парсер и редактор требований во frontend.
- Результат: на всех трёх тестовых вакансиях получаем адекватный список требований.

### J2. Хранение профиля и результатов сопоставления
*Простыми словами:* резюме разбирается один раз, профиль сохраняется. Результаты по каждой вакансии тоже сохраняются, чтобы не гонять LLM повторно.

- Поле `profile_json` в `parsed_resume`; таблицы для результатов (сессия сопоставления, результат по вакансии, результат по требованию со статусом `NOT_STATED`).
- Кэш по хэшу резюме и версии шаблона.

### J3. Эндпоинт «резюме → список вакансий»
*Простыми словами:* загружаешь одно резюме, выбираешь вакансии (или «все»), получаешь рейтинг.

- `POST /matches` возвращает `202` и id, `GET /matches/{id}` отдаёт прогресс и результат.
- Резюме парсится один раз, затем оценки по вакансиям идут параллельно с ограничением числа одновременных вызовов.
- Если одна вакансия упала, остальные всё равно показываем.

### J4. Рейтинг и карточка результата
*Простыми словами:* то, что увидит рекрутер: порядок вакансий и почему именно так.

- Сортировка по `score`, тай-брейк по покрытию обязательных требований, текст «почему на этом месте».
- Таблица требований, сильные стороны, пробелы, риски, вопросы кандидату.
- Дополнительная проверка в Java: цитата обязана быть подстрокой резюме (`EvidenceValidator`), иначе статус понижается до `NOT_STATED`.
- Обновить `openapi.yaml`.

### J5. Надёжность
*Простыми словами:* система не должна падать на плохих входных данных.

- Пустой, битый и нестандартный файл дают понятную ошибку.
- Таймауты и недоступность Python/LLM не ломают всё.
- Тесты на каждый случай.

### J6. Запуск и документы

- Проверка `docker compose up` в чистом окружении, README, схема потока данных, два use case.
- Профиль `mock-llm` для запуска без ключа.

### J7. Если останется время

- PDF-отчёт.
- Реальная NER-модель для имён.
- Сравнение нескольких резюме на одной вакансии (старый ATS-рейтинг).

## Python-сервис (`scoring-service`)

Работает без Java: на вход тексты и JSON, на выход структура из контракта.

### PY1. Математика (без LLM, можно начинать сразу)
*Простыми словами:* из статусов («подтверждено / частично / нет / не указано») и стажа получается один балл от 0 до 100.

- Чистые функции:
  - вес требования по типу (обязательное > желательное > необязательное);
  - стаж по формуле «сколько есть / сколько нужно», не больше 1;
  - `NOT_STATED` даёт 0 в нижней границе и 1 в верхней: расширяет вилку, но не штрафует.
- Golden-тесты с конкретными числами. Один набор правил на все вакансии.

### PY2. Разбор резюме (`ParseResume`)
*Простыми словами:* LLM читает текст резюме и раскладывает его по полочкам.

- Работает через OpenRouter, в тестах через `mock-llm`; схема ответа строгая.
- **Стаж и длительность считает код по датам**, а не берёт из текста («2 года» в резюме может не совпадать с датами). Расхождения идут в `warnings`.
- Каждый факт с цитатой, цитата проверяется как подстрока.
- Повтор при плохом JSON, защита от инъекций в тексте.

### PY3. Сопоставление (`EvaluateMatch`)
*Простыми словами:* для каждого требования вакансии модель ищет в резюме подтверждение и ставит статус.

- Правила статусов в промпте:
  - нет сведений → `NOT_STATED`, а не `NONE`;
  - упомянуто косвенно, похожая область, мало стажа → `PARTIAL`;
  - синонимы и контекст учитываются («Excel» подходит под «работа с таблицами»).
- Цитата проверяется кодом; не прошла проверку → `NOT_STATED`.
- Вызывает PY1 для расчёта баллов.

### PY4. Объяснения и вопросы
*Простыми словами:* из результатов сопоставления собираются сильные стороны, пробелы, риски и 3–5 вопросов кандидату.

- Вопросы строятся из `NOT_STATED`, `PARTIAL` и предупреждений о датах.
- Каждое утверждение привязано к цитате или требованию, выдумывать факты нельзя.
- Короткий `recruiter_note` для дальнейшей коммуникации.

### PY5. Надёжность и скорость

- Таймауты, повторы, ограничение параллелизма, понятные коды ошибок в gRPC.
- Кэш разбора резюме по хэшу текста.
- Режим «mock» для CI и демо без ключа.

### PY6. Набор проверок 4 резюме × 3 вакансии
*Простыми словами:* скрипт, который гоняет все пары и сверяет с ожидаемым порядком.

- Алексей → вакансия 1 первая; Лилия: вакансии 2 и 3 дают разные объяснимые баллы.
- Нужен и для защиты: можно показать метрики и объяснения.

### PY7. Если останется время

- «Сила доказательства» (самодекларация весит меньше подтверждённого факта).
- Смежные навыки.
- Гиперпараметры по уровню.

## Точки синхронизации

| Точка | Когда | Что проверяем |
|---|---|---|
| **Т0** | Конец шага 0 | proto заморожен, заглушка отдаёт реалистичные данные, Java-клиент собирается |
| **Т1** | Готовы J3 и PY3 | переключаем `SCORING_GRPC_TARGET` с заглушки на реальный сервис и прогоняем 4×3 |
| **Т2** | Готовы J4 и PY4 | карточка результата показывает настоящие вопросы и риски |
| **Т3** | Готовы J5, J6, PY5 | чистый запуск по README, репетиция демо |

Если контракт нужно менять после Т0, меняем оба конца одним коммитом и обновляем заглушку, чтобы Java не ломалась молча.
