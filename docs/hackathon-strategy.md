# Стратегия хакатона: закрываем ТЗ, потом расширяем

Задача 3 «Сравнительный анализ резюме и вакансий». Состояние сервиса на 2026-11-12 (`ats-service`, ветка `feature/unified-ats-service`).

## 1. Главное: ТЗ развернуло направление

Сейчас система построена как ATS: одна вакансия, много резюме, рейтинг кандидатов. По ТЗ нужно обратное: **одно резюме и набор вакансий, на выходе рейтинг вакансий для кандидата**. Тестовые вакансии к тому же не только IT: frontend, учёт основных средств, куратор образовательного процесса.

Выводы:

1. **Сопоставление, то есть ядро ТЗ, сейчас заглушка.** `scoring-service` отдаёт `0.5`, а на сопоставление и ранжирование приходится 40 из 100 технических баллов.
2. **Нужно развернуть поток**: резюме разбирается один раз, потом оценивается против N вакансий.
3. **Нужен статус «не указано».** Сейчас в отчёте только `COVERED/PARTIAL/GAP`. Критерий 5 требует не считать отсутствие сведений отсутствием навыка.
4. **Модель требований слишком «навыковая».** Для вакансий 2 и 3 требования это образование, стаж 3+ года «в одном из направлений», soft skills и обязанности. Каталог навыков с `skill_id` тут не работает.

## 3. Приоритеты

### P0. Закрыть ТЗ (строго по порядку)

**P0.1. Модель требований для любых вакансий** (критерий 1, 16 баллов)
- Добавить в `vacancy_requirement` поле `category`: `SKILL / EXPERIENCE / EDUCATION / SOFT / OTHER`. Для опыта и образования `years_required` уже есть.
- Промпт v3 с одним правилом для всех вакансий: «Требования» дают `MUST`, «Будет плюсом / преимуществом» дают `NICE`. «Обязанности» дают производные требования с пометкой `source=DUTY` и меньшим весом (в вакансии 3 в «Требованиях» почти пусто, суть в обязанностях). «Условия» в требования не попадают, кроме явных просьб вроде «укажите, подходит ли расположение».
- OR-требования («бухгалтер по ОС и ТМЦ, или складской учёт, или инвентаризация») хранятся как одно требование.

**P0.2. Разбор резюме в структурированный профиль** (8 баллов)
- В `scoring-service` один LLM-вызов: резюме → JSON из мест работы, дат, образования, навыков и цитат.
- **Длительность считает код по датам**, а не берёт из текста. Дату «сейчас» делаем параметром.

**P0.3. Сопоставление и скоринг** (24 балла)
- Для каждого требования LLM отдаёт `status` (`FULL / PARTIAL / NONE / NOT_STATED`), цитату из резюме и комментарий. Цитату проверяет код.
- Арифметику считает код по упрощённой модели `q = m·t·ρ`: `m` из статуса, `t = min(1, годы / требуемые годы)`, вес по `kind` (MUST > NICE > OPTIONAL).
- **`NOT_STATED` не штрафуется**: 0 в `score_low`, 1 в `score_high`. Это ложится на существующий контракт с вилкой.
- Golden-тесты с цифрами. Одна формула для всех документов, без подстройки под отдельную вакансию.

**P0.4. Поток «резюме → N вакансий»** (16 баллов)
- Эндпоинт `POST /matches`: файл резюме и список `vacancyId` (или все активные). Ответ: ранжированный список с `score`, `score_low`, `score_high` и объяснением позиции.
- Резюме парсим один раз, затем N вызовов оценки параллельно, кэш по хэшу резюме и версии шаблона.
- Старый ATS-путь не ломаем и не развиваем.

**P0.5. Результат для рекрутера** (12 баллов)
- Таблица «требование / подтверждение (цитата) / статус / комментарий».
- Сильные стороны, пробелы и риски, рекомендации и 3–5 вопросов кандидату (из `NOT_STATED`, `PARTIAL` и расхождений вроде несовпадения дат).
- Текст коммуникации только из подтверждённых фактов, с той же проверкой цитат.

**P0.6. Frontend для сквозного сценария** (6 + 10 баллов отраслевых)
- Экран «Загрузить резюме, выбрать вакансии» и экран результата: рейтинг, раскрывающаяся таблица по каждой вакансии, блок «вопросы / риски».
- Слепой режим показываем как фичу, reveal можно отложить.

**P0.7. Надёжность** (12 баллов)
- Пустой, битый и нестандартный файл, ошибка LLM: понятная ошибка в UI, а не 500.
- Прогон на 4 резюме × 3 вакансии и на файлах другой структуры.

**P0.8. Развёртывание и документы** (20 баллов)
- `docker compose up` в чистом окружении по README без правки кода; профиль `mock-llm` позволяет запуститься без ключа.
- README: требования, запуск и остановка, переменные, внешние сервисы.
- Архитектура и поток данных, минимум два use case с входом и ожидаемым выходом (например, «Алексей → вакансия 1» и «Лилия → вакансии 2 и 3»).

### P1. Если останется время

1. PDF-отчёт для рекрутера.
2. Реальная NER-модель: сейчас `fake`, имена не маскируются.
3. Сравнение нескольких резюме на одной вакансии (прежний ATS-рейтинг как доп. фича).
4. «Сила доказательства»: самодекларация весит меньше подтверждённого факта.
5. Слайд с дорожной картой для критерия «план развития».

### P2. После хакатона

hh-импорт, GitHub-обогащение, auth/RBAC, `ml-trainer`, смежные навыки (Kafka vs RabbitMQ), анализ интервью.

## 4. На что обратить внимание в тестовых данных

- **Лилия.** В вакансии 2 нужен стаж по учёту ОС, ТМЦ или складу, а в резюме просто «бухгалтер». Это `PARTIAL` или `NOT_STATED` с вопросом, но не `NONE`. Вакансия 3 (комплектность документов, делопроизводство, Excel) может оказаться для неё сильнее вакансии 2. Система должна объяснить такой результат.
- У Лилии на последнем месте указано «10 месяцев», а по датам уже больше года.
- **Алексей.** В резюме «март 2023 — настоящее время (2 года)», по датам около 3,7 года. Это ловушка и повод для вопроса кандидату. Он должен уверенно выйти на вакансию 1, а на вакансиях 2 и 3 получить низкий балл с понятными пробелами (быстрый sanity-тест всей логики).

## 5. Риски

1. **Бесплатная модель** (`dots-3-note:free`, таймауты до 300 с, `429`) × N вакансий на резюме. Нужны ограничение параллелизма, кэш и заранее записанный прогон для демо; возможно, дешёвая платная модель на защиту.
2. **Время на защите.** Если оценка идёт минутами, показывать прогресс по каждой вакансии.
3. **Разрастание scope.** Каждую идею сверяем с вопросом «какой пункт ТЗ она закрывает».
