# ТЗ: dictionary-service и нормализация навыков

Статус: реализовано в ветке `feature/skill-dictionary-service` (ядро сервиса, админка в ats, интеграция со scoring). Ниже — решения, принятые по итогам ревью; они имеют приоритет над исходным черновиком.

## 0. Принятые решения (актуальная реализация)

| Тема | Решение |
|---|---|
| Владелец словаря | Отдельный `dictionary-service` (Python 3.12, gRPC), схема `dictionary` в Postgres |
| Админка | REST BFF в `ats-service` (`/api/v1/admin/dictionary`); `dictionary-service` — внутренний gRPC |
| Проверка ссылок | В `ats`: `vacancy_requirement` + `skill_kind_stat`; удаление используемого навыка — 409 |
| Merge | Нет. Только удалить алиас и привязать заново; неиспользуемый навык удаляется |
| Канонический алиас | Только `skill_alias.is_canonical` + partial unique index; `canonical_alias_id` убран |
| Тип навыка | `skill_type {TECH, TOOL, DOMAIN, SOFT, OTHER}`; профессии и допуски — не навыки |
| Версия | `resolver_version = dictionary_version + embedding_model_id + config_hash + pymorphy_version + homoglyph_rules_version` |
| Запуск | Фиксирует `resolver_version`; `Resolve` принимает `as_of_resolver_version`; снимки версий в БД |
| Деградация | При недоступности словаря scoring продолжает работу по точному ключу (`EXACT_FALLBACK`) |
| Эмбеддинги | В v1 только подсказки в очереди NEW; на матчинг не влияют |
| Fuzzy для навыков | Убран. Сравнение по `skill_id` или точному ключу |
| Не-IT | Seed включает инструменты и домены (1С:Бухгалтерия, Excel, учёт ОС/ТМЦ, делопроизводство) |
| Контексты ревью | Только обезличенные строки, без `resume_id`/`vacancy_id` |

Исходные разделы ниже сохранены как история; расхождения с разделом 0 трактуются в пользу раздела 0.

## 1. Цель

1. Вынести словарь навыков и всю логику нормализации в отдельный сервис, чтобы `ats-service` и `scoring-service` не ходили друг к другу за словарём и не дублировали код: оба обращаются только к `dictionary-service`.
2. Применять **один и тот же конвейер** к навыкам вакансии и навыкам резюме (устранить асимметрию: `js` в резюме не находил `javascript` из вакансии).
3. Дать HR админку: сюда попадают нераспознанные (NEW) навыки, HR привязывает их к существующему навыку как алиас, создаёт новый навык или отклоняет.
4. Закрыть сопутствующие дефекты, найденные разведкой (неподтверждённый шаблон, ложный fuzzy, воспроизводимость).

## 2. Вне рамок этого ТЗ

- Иерархия и смежность навыков (PostgreSQL → SQL, Kafka ~ RabbitMQ). Отдельный RFC и golden-тесты.
- Полная админка (роли, аудит, массовые операции). Сейчас только очередь NEW и управление алиасами.
- Реальные вызовы LLM из тестов. Тесты используют моки; ручная проверка на стороне заказчика.

## 3. Архитектура

### 3.1 Новый сервис `dictionary-service`

| Аспект | Решение |
|---|---|
| Язык | Python (нужны pymorphy3 и эмбеддинги). Вариант Java обсуждению не подлежит, пока не доказана необходимость. |
| API | gRPC для сервисов (`Resolve`, `GetVersion`), REST для админки (HTTP/JSON) |
| Хранилище | Своя схема в Postgres; схема и seed накатываются Liquibase (`017`, `018`), сервис не делает runtime DDL |
| Эмбеддинги | Модель `bge-m3` или `multilingual-e5` локально, векторы словаря считаются при старте и при изменении словаря, хранятся в памяти (несколько тысяч записей, векторная БД не нужна) |
| Сборка | Свой Dockerfile, запись в docker-compose и в k8s-манифесты по аналогии с остальными сервисами |

Принцип: **словарь принадлежит только dictionary-service**. Остальные сервисы не читают его таблицы напрямую.

### 3.2 Кто и когда вызывает

- `scoring-service` принимает **исходный текст распарсенного резюме** (и требования вакансии) и возвращает скор. LLM в scoring-service ссылается на цитаты из оригинального текста, поэтому канонизация **никогда не подменяет текст резюме**: канон и `skill_id` хранятся рядом с сырым именем и цитатой, а цитаты остаются дословными подстроками оригинала.
- Словарь `scoring-service` использует **на этапе матчинга**: после извлечения навыков из резюме он делает **один batch-вызов `Resolve`** со всеми сырыми именами навыков обеих сторон (резюме + требования вакансии) и дальше сравнивает по `skill_id`. Один запуск скоринга = одна `dictionary_version`, она сохраняется в результате запуска.
- `ats-service` вызывает `Resolve` только при разборе и сохранении шаблона вакансии (чтобы HR видел «из словаря / новый навык» и чтобы NEW попадали в очередь ревью). Канонизировать `ParsedResume` после `ExtractResume` в ats **не нужно**. В БД ats для требований вакансии сохраняются `skill_id`, `canonical_name`, `method`, `confidence`, `dictionary_version`.
- Прямых вызовов `scoring-service` ↔ `ats-service` ради словаря нет: оба ходят только в dictionary-service.
- Отказоустойчивость: у вызова из scoring-service таймаут и ограниченные ретраи. Если dictionary-service недоступен, запуск завершается понятной ошибкой; тихая деградация до точного совпадения ключей не допускается, чтобы не получить неповторяемые результаты.

### 3.3 Миграция данных

- Перенести `skill` и `skill_alias` (84 навыка, 105 алиасов, seed) из миграций ats в dictionary-service с сохранением `skill_id` (чтобы не сломать `skill_kind_stat` и уже сохранённые шаблоны).
- В ats оставить только ссылки на `skill_id` без внешних ключей на чужую схему (ссылочная целостность на уровне приложения).
- Удалить из ats `SkillCatalog`, `NewSkillWriter` и логику создания навыков; `SkillNormalizer` заменить клиентом dictionary-service.
- В scoring-service удалить копию `normalize.py` (и нормализацию `normalize_key` в `mapping.py`), вместо неё клиент dictionary-service (источник правды один).

## 4. Конвейер нормализации (`Resolve`)

Вход: пачка строк (`raw_name`, `lang_hint?`, `context?`). Выход для каждой: `skill_id?`, `canonical_name`, `normalized_key`, `method`, `confidence`, `candidates[]`, и общий `dictionary_version`.

Этапы по порядку:

1. **Нормализация ключа.** Как сейчас: NFKC, схлопывание пробелов, lowercase, снятие краевой пунктуации; `+`, `#`, ведущая точка сохраняются.
2. **Свёртка гомоглифов.** Если токен содержит латинские буквы или цифры и при этом кириллические двойники (`А В Е К М Н О Р С Т У Х`, строчные аналоги), заменить их латинскими. Чисто кириллические токены не трогать. Примеры: `1С` → `1c`, `С++` → `c++`, `Еxcel` → `excel`.
3. **Лемматизация кириллических токенов** (pymorphy3). Латиницу не трогать. Ключ строится из лемм: `кубернетесом` → `кубернетес`, `бухгалтерского учёта` → `бухгалтерский учёт`. Результат проверяется на тестовом наборе, для заимствований леммы могут быть странными: исключения решаются алиасом.
4. **Точный поиск по алиасам** (`skill_alias.alias_normalized`, ключ строится теми же этапами 1–3 при записи алиаса).
5. **Эмбеддинг-fallback.** Ближайший канон/алиас по косинусной близости. Две зоны, пороги в конфиге:
   - `>= T_HIGH` → разрешён на лету (`method=EMBEDDING`), **в словарь не записывается**; попадает в очередь ревью как кандидат на подтверждение;
   - `T_LOW .. T_HIGH` → не разрешён, в очередь ревью с кандидатами (top-3);
   - `< T_LOW` → NEW.
   Стартовые значения порогов консервативные (например `T_HIGH=0.88`, `T_LOW=0.75`), **подлежат калибровке** на размеченных парах (раздел 8).
6. **NEW.** Навык не получает `skill_id`, в ответе `method=NEW`, `skill_id=null`. Создаётся (или обновляется счётчик) запись в очереди ревью. Для матчинга до решения HR используется `normalized_key` (точное совпадение).

Обязательно для вызывающей стороны: хранить `raw_name`, `canonical_name`, `method`, `confidence`, `dictionary_version`. Сырое имя и цитата из оригинала не перезаписываются каноном.

## 5. Модель данных dictionary-service

```
skill(
  id, status {ACTIVE, DEPRECATED}, kind {TECH, TOOL, PROFESSION, SOFT, OTHER},
  canonical_alias_id, created_at, updated_at
)

skill_alias(
  id, skill_id, alias_raw, alias_normalized UNIQUE,
  is_canonical bool,            -- ровно один true на skill
  lang {ru, en, mixed},
  source {SEED, HR, LLM, EMBEDDING_CONFIRMED},
  created_by, created_at
)
  -- partial unique index: (skill_id) WHERE is_canonical
  -- alias_normalized уникален глобально: один алиас не может вести на два навыка

review_item(
  id, normalized_key UNIQUE, sample_raw[], occurrences, first_seen, last_seen,
  status {PENDING, RESOLVED_ALIAS, RESOLVED_NEW_SKILL, REJECTED},
  suggested_skill_id?, suggested_confidence?, candidates JSON,
  resolved_skill_id?, resolved_by?, resolved_at?
)

dictionary_meta(version BIGINT)   -- инкремент при любом изменении skill/skill_alias
```

Требование заказчика: **из всех алиасов навыка ровно один нормализованный (канонический)**; он отображается в UI и в отчётах. Смена канонического алиаса атомарна (в одной транзакции снимается старый флаг, ставится новый).

## 6. Админка

REST API dictionary-service + раздел во фронтенде ats (минимальный UI). Расширяется позже, поэтому структуру делаем с запасом: отдельный раздел «Словарь» с вкладками.

### 6.1 Вкладка «Очередь NEW»

- Список `review_item` со статусом PENDING: сырые написания, число вхождений, примеры контекста (из какой вакансии/резюме), предложенные кандидаты и их близость.
- Действия HR:
  1. **Привязать как алиас** к существующему навыку (поиск по каноническому имени и алиасам);
  2. **Создать новый навык** (задать каноническое имя, `kind`);
  3. **Отклонить** (мусор, не навык, например длинная цитата из вакансии).
- После решения: пишется алиас/навык, `dictionary_version++`, запускается перерезолв затронутых данных (см. 7.4).

### 6.2 Вкладка «Навыки»

- Список навыков, фильтры по `kind`, статусу, поиск.
- Карточка навыка: список алиасов, один помечен каноническим, кнопки «сделать каноническим», «добавить алиас», «удалить алиас».
- **Merge:** слить навык A в навык B (алиасы A переезжают в B, A получает DEPRECATED, `skill_id` A переадресуется на B). Необходимо, чтобы словарь не крошился.

### 6.3 Валидации

- Попытка добавить алиас, который уже ведёт на другой навык: отказ с указанием конфликта и предложением merge.
- Нормализация введённого алиаса делается тем же конвейером (этапы 1–3), чтобы ключ совпадал.

## 7. Сопутствующие фиксы

### 7.2 Проверка подтверждённого шаблона

- Перед запуском скоринга проверять `is_confirmed`. Если шаблон не подтверждён: отказ с понятной ошибкой, а не отправка цитаты вместо `skill_name`.

### 7.3 Fuzzy-матчинг в scoring-service

- После канонизации (batch `Resolve`, см. 3.2) сравнение идёт по `skill_id`: равны → `1.0`.
- `SequenceMatcher` убрать из пути навыков с `skill_id`. Для нераспознанных (NEW, без `skill_id`) оставить точное совпадение `normalized_key`; fuzzy допускается только для токенов длиной от 6 символов и без расхождения значимых токенов (устраняет `vue/vuex = 0.85` и ложный partial на `1С:Бухгалтерия`).
- Замена значений `S^{ij}` для несовпавших пар (эмбеддинги вместо fuzzy) выносится в отдельный этап (раздел 9, этап 5): требует калибровки и golden-тестов.

### 7.4 Воспроизводимость и перерезолв

- `dictionary_version` сохраняется: в версии шаблона вакансии и в записи запуска скоринга (вместе с трассой навыков резюме: сырое имя, канон, способ, confidence).
- Передаётся в gRPC в ответе `Resolve` и в запросах/ответах скоринга.
- Уже сохранённые шаблоны: фоновая задача перерезолва для NEW-навыков при появлении алиаса (по `normalized_key`); для старых запусков версия остаётся прежней, результат не пересчитывается молча.

### 7.5 UI результатов

- В отчёте по резюме показывать: сырое имя из резюме → канон → способ (`alias` / `embedding` / `new`) → confidence; цитаты дословные из оригинала.
- Для требований вакансии оставить «из словаря / новый навык», добавить способ разрешения.

### 7.6 mock-scoring-service

- Убрать собственный мини-словарь на 36 навыков. Заглушка либо вызывает dictionary-service так же, как настоящий scoring-service, либо использует общий набор тестовых фикстур, выгруженный из seed dictionary-service, чтобы демо не расходилось с реальным поведением.

## 8. Генерация синонимов через LLM

Цель: расширить словарь с 105 алиасов до нескольких тысяч с покрытием русского рынка и **не-IT профессий**.

### 8.1 Входной список

Файл `seed/specialties.yaml`: самые популярные специальности и их типичные навыки/инструменты. Минимальный набор (расширяется заказчиком):

- IT: Java/Python/JS/frontend/QA/DevOps/аналитик/продакт/дизайнер и их стек;
- не-IT: бухгалтер, специалист по учёту ОС и ТМЦ, экономист, юрист, HR-менеджер, менеджер по продажам, библиотекарь, электрик, учитель/преподаватель, куратор образовательного процесса, секретарь/делопроизводитель, инженер-технолог, логист, закупщик, врач/медсестра, водитель.

Для каждой записи: каноническое название, `kind`, язык канона.

### 8.2 Генерация офлайн-инструмент для наполнения словаря

- Скрипт (CLI) в dictionary-service: для каждой записи запрашивает у LLM алиасы по категориям: русский вариант, транслитерация, жаргон/сокращения, частые опечатки, формулировки из вакансий hh. Падежные формы **не нужны** (закрывает лемматизация).
- Ответ строго JSON по схеме (`canonical`, `aliases[{text, lang, category}]`); валидация схемы, повторный запрос при невалидном ответе.
- LLM-клиент берётся из существующего модуля (тот же провайдер и конфиг). Тесты скрипта только на моках.

### 8.3 Пост-обработка и ревью

- Результат пишется **не в боевые таблицы**, а в staging (`alias_draft`, статус DRAFT).
- Автоматические проверки: дедуп по `alias_normalized`; конфликт с уже существующим алиасом другого навыка помечается и не импортируется; слишком общие слова (`разработчик`, `специалист`) отсеиваются по стоп-листу; длина алиаса ограничена.
- Экспорт в CSV/MD для вычитки глазами; импорт только подтверждённых строк как `source=LLM`.
- После импорта `dictionary_version++`.

### 8.4 Стартовые данные для калибровки

- Собрать 150–200 размеченных пар «то же / не то же» (например `js/javascript`, `питон/python`, `1С/1C`, `vue/vuex`, `java/javascript`, `бухгалтер/бухгалтерский учёт`) для подбора `T_HIGH`/`T_LOW`. Пары хранить в `tests/golden/skill_pairs.yaml`.

### 8.5 Генерация по специальности из админки

Дополнение к 8.1–8.3: HR сам вводит специальность в админке и получает черновики навыков и синонимов для неё, без правки `specialties.yaml` и запуска CLI.

**Границы.** `Resolve` по-прежнему **никогда не вызывает LLM**. LLM используется только по явному действию HR в админке. Генерация и CLI из 8.2 используют **одно общее ядро** (промпт, схема ответа, валидация, повтор при невалидном JSON), в сервисе оно одно. Для вызова LLM у dictionary-service свой конфиг (провайдер, модель, ключ через переменные окружения); ссылка «берётся из существующего модуля» из 8.2 к этому пункту не относится.

**Сценарий в UI (новая вкладка «Генерация» в разделе «Словарь»).**

1. HR вводит специальность свободным текстом («Бухгалтер», «Электромонтёр», «Библиотекарь») и при желании: `kind` для результата, максимальное число навыков (по умолчанию 30), короткое примечание-контекст.
2. Кнопка «Сгенерировать» создаёт задачу генерации. Статусы задачи: `PENDING → RUNNING → DONE / FAILED`. Выполняется асинхронно, UI опрашивает статус.
3. Что делает LLM (одним структурированным запросом или двумя шагами, на усмотрение исполнителя, результат единый):
   - выдаёт список типичных навыков, инструментов и терминов для специальности (канон + `kind`);
   - для каждого и для самой специальности выдаёт алиасы по тем же категориям, что в 8.2 (русский вариант, транслитерация, жаргон/сокращения, частые опечатки, формулировки из вакансий hh). Падежные формы не нужны.
4. Ответ строго JSON по схеме `{specialization, skills:[{canonical, kind, aliases:[{text, lang, category}]}]}`; валидация схемы, повтор при невалидном ответе, затем `FAILED` с понятной причиной.
5. Результат попадает **только в staging** (`alias_draft`, статус DRAFT), боевые таблицы не меняются. К записям применяются автоматические проверки из 8.3.

**Экран ревью черновиков.**

- Черновики сгруппированы по навыкам: канон, алиасы с чекбоксами, `kind`, пометки.
- Если канон из ответа LLM уже есть в словаре (определяется конвейером `Resolve`, этапы 1–4), черновик показывается как «добавление алиасов к существующему навыку», дубль навыка не создаётся.
- Алиас, который уже принадлежит другому навыку, помечается конфликтом (с указанием владельца) и не может быть подтверждён без правки или merge (см. 6.3).
- HR может править текст алиаса, менять канонический, снимать отдельные алиасы, отклонять навык целиком.
- «Подтвердить выбранное» пишет навыки и алиасы с `source=LLM`, у каждого навыка выставляется ровно один канонический алиас, `dictionary_version` увеличивается **один раз** за действие подтверждения. Автоматического подтверждения нет.

**REST (минимум).**

- `POST /admin/generation-jobs` (`specialization`, `kind?`, `max_skills?`, `note?`) создаёт задачу;
- `GET /admin/generation-jobs` и `GET /admin/generation-jobs/{id}` статус и черновики;
- `POST /admin/generation-jobs/{id}/approve` (список принятых черновиков и правок);
- `POST /admin/generation-jobs/{id}/reject`.

**Ограничения.**

- Одновременно выполняется одна задача; лимит `max_skills` и таймаут на вызов LLM в конфиге; ошибка LLM переводит задачу в `FAILED`, ничего не пишется.
- В задаче сохраняются специальность, автор, время и сырой ответ LLM (для разбора спорных алиасов).
- Дополнения к модели данных: `generation_job(id, specialization, kind?, note?, status, requested_by, created_at, finished_at, error?, raw_response?)`; в `alias_draft` добавить `generation_job_id`, `canonical`, `target_skill_id?` (если добавление к существующему), `conflict_skill_id?`, статусы `DRAFT / APPROVED / REJECTED`.
- Тесты только на моках LLM; реальную генерацию на живой модели проверяет заказчик вручную.

## 9. Этапы работ

1. **Каркас dictionary-service:** схема БД, миграция seed с сохранением `skill_id`, gRPC `Resolve` с этапами 1–4 (ключ, гомоглифы, лемматизация, алиасы), `dictionary_version`, docker/k8s. Клиент в ats (только шаблон вакансии) и в scoring-service (batch `Resolve` при матчинге для резюме и требований), удаление дублей `SkillCatalog` / копии normalize.
2. **Фиксы 7.2 и 7.1:** проверка `is_confirmed`, типы требований и заполнение proto-вариантов; сохранение трассы разрешения (7.4, 7.5).
3. **Админка:** очередь NEW, алиасы, канонический флаг, merge, перерезолв.
4. **Генерация словаря (раздел 8):** общее ядро генерации, скрипт, staging, вычитка, импорт; генерация по специальности из админки (8.5).
5. **Эмбеддинг-fallback и замена fuzzy** (4.5, 7.3): калибровка порогов на golden-парах, флаг включения. Этот этап меняет значения скоринга, поэтому отдельный запуск и сравнение метрик до/после.

Этапы 1–2 дают результат на js/питон/1С сразу и не меняют формулу.

## 10. Критерии приёмки

| Кейс | Ожидание |
|---|---|
| вакансия `JavaScript`, резюме `js` | один `skill_id`, `S = 1.0` |
| `питон` / `python` | один `skill_id` |
| `кубы`, `кубернетес`, `кубернетесом`, `k8s` | один `skill_id` Kubernetes |
| `1С` (кириллица) и `1C` (латиница) | один ключ |
| слова «сок», «бухгалтер» | гомоглифы не применяются, слова не искажаются |
| `vue` / `vuex` | разные навыки, не `0.85` |
| неизвестный навык | `method=NEW`, появляется в очереди, не создаёт `skill_id` молча |
| HR привязывает NEW как алиас | `dictionary_version` растёт, следующий резолв даёт `skill_id`, затронутые NEW переразрешены |
| попытка алиаса с конфликтом | отказ с указанием навыка-владельца |
| у навыка более одного канонического алиаса | невозможно (ограничение БД) |
| шаблон не подтверждён | скоринг не запускается, понятная ошибка |
| требование «ведение учёта ОС и ТМЦ» | уходит не как `SkillRequirement` |
| запуск скоринга | сохранён `dictionary_version`, он один на весь запуск (один batch `Resolve`) |
| отчёт по резюме | видно: сырое имя → канон → способ → confidence |
| цитаты из резюме в отчёте | дословные подстроки оригинального текста, канонизация их не меняет |
| dictionary-service недоступен | запуск скоринга падает с понятной ошибкой, без тихой деградации |
| HR вводит специальность в админке | создаётся задача, по завершении появляются черновики, боевые таблицы не изменены |
| канон из ответа LLM уже есть в словаре | черновик показан как добавление алиасов к существующему навыку, дубль навыка не создаётся |
| алиас из черновика принадлежит другому навыку | помечен конфликтом, подтвердить нельзя без правки или merge |
| HR подтверждает черновики | алиасы записаны с `source=LLM`, у навыка ровно один канонический, `dictionary_version` вырос один раз |
| невалидный JSON или ошибка LLM | повтор, затем задача `FAILED` с причиной, черновиков нет |
| `Resolve` | LLM не вызывается ни при каких условиях |

Технические критерии: unit-тесты этапов 1–4 (гомоглифы и лемматизация с отдельными таблицами кейсов), контрактные тесты gRPC, интеграционные тесты ats → dictionary-service и scoring-service → dictionary-service, тесты генерации (CLI и админка) на моках LLM, golden-тест пар из 8.4 (для этапа 5), реальный LLM в тестах не вызывается.

## 11. Риски и открытые вопросы

- **Лемматизация заимствований:** pymorphy3 может давать странные леммы для `кубернетес`, `докер`. Митигация: прогон по seed и golden-парам; проблемные случаи решаются алиасом.
- **Эмбеддинги путают похожее:** `Java/JavaScript`, `Vue/Vuex`. Митигация: на этапе 5 не автозаписывать в словарь, держать пороги консервативными, golden-тесты на «не то же» пары.
- **LLM-алиасы могут содержать выдумки:** обязательная вычитка перед импортом и подтверждение HR, автоподтверждения нет.
- **LLM в dictionary-service (только админка, 8.5):** нужны ключ и конфиг провайдера, лимиты на число навыков и одну задачу за раз, чтобы не получить неконтролируемые расходы. Митигация: `Resolve` без LLM, генерация только по действию HR.
- **Ресурсы:** модель эмбеддингов добавляет память и время старта dictionary-service; выбрать размер модели с учётом доступного железа.
- **Синхронная зависимость scoring-service от dictionary-service:** митигация: один batch-вызов на запуск, таймаут и ретраи, понятная ошибка при недоступности.
- **Открыто:** (1) где жить модели эмбеддингов для семантического матчинга текстовых требований: отдельный эндпоинт `Embed` в dictionary-service (scoring уже ходит туда) или своя модель в scoring-service; (2) нужен ли `kind=PROFESSION` как отдельный тип в словаре или профессии идут только через `TextRequirement` (от этого зависит, как в 8.5 записывается сама специальность); (3) как показывать HR очередь NEW при больших объёмах (пагинация, группировка по контексту); (4) политика перерезолва уже сохранённых шаблонов: автоматически или по кнопке.
