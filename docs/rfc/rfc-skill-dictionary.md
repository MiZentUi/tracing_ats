# RFC: справочник навыков — источники, данные, способ поставки

> [!NOTE]
> Документ собирает **внешние источники** данных о навыках и фиксирует варианты
> поставки справочника. Итоговое решение о способе поставки принимает команда;
> здесь описаны последствия каждого варианта.

## 1. Контекст

Пайплайну извлечения признаков (`docs/rfc/rfc-feature-extraction.md`) нужны три
вещи:

1. **нормализация** — свести `k8s`, `Kubernetes`, `кубернетес` к одному
   `normalized_name`;
2. **иерархия** — понимать, что `PostgreSQL` — это `SQL`, а `Docker` относится к
   контейнеризации;
3. **смежность** — знать, что `Kafka` и `RabbitMQ` близки, но не равны.

Ветка `feature/vacancy-skill-kinds` (пока не вмержена) реализовала первый пункт —
**нормализацию**, и только её. Иерархии и смежности нет.

### 1.1. Что уже есть в проекте

| Что | Где | Состояние |

Практический вывод: справочник — не гринфилд. Нормализация уже работает в Java,
и спор идёт только о том, как её **разделить** с `scoring-service`, а не о том,
создавать ли её. Без групп и смежности пайплайн A остаётся точным совпадением
плюс морфология: это рабочий старт (A0–A1), но не целевой A3.

## 2. Три типа данных — их нельзя смешивать

| Тип | Пример | Что это | Откуда берётся |
|---|---|---|---|
| **Алиасы** | `k8s` = `kubernetes`, `постгрес` = `postgresql` | равенство, не похожесть | готовые справочники, курирование |
| **Иерархия** | `PostgreSQL` → `SQL` → `базы данных` | классы родства | ESCO, Wikidata, Lightcast |
| **Похожесть** | `Kafka` ~ `RabbitMQ` = 0.6 | число в `[0;1]` | почти всегда расчёт или проприетарный API |

Алиасы можно брать из открытых источников почти без ограничений. Иерархия даёт
**классы**, а не числа. Численная похожесть в открытом доступе практически
отсутствует: числа, которые попадут в `S^{ij}`, — это формула, и по `AGENTS.md`
§6 они фиксируются в `rfc-scoring-model.md`, а не импортируются из чужого API.

### Замечания по источникам

- **ESCO** — де-факто стандарт в ЕС для matching; формат SKOS/RDF, удобно
  конвертировать в свой JSON. Отсутствие русского — главный минус.
- **O*NET** обновляется ежеквартально, раз в год — мажорно (31.0 — текущая
  версия). `Technology Skills` — самый полезный файл для IT.
- **Lightcast** — единственный источник, где «related skills» уже посчитаны, но
  API требует регистрации, а условия использования надо читать до демо.
- **Wikidata** даёт русские алиасы бесплатно, но без гарантии качества: один и
  тот же навык может иметь десяток формулировок, часть — мусорные.
- **Linguist** и **Stack Overflow** закрывают именно технический стек, где
  вариативность написания максимальна.

## 4. Почему нет готовой «похожести»

1. **Проприетарные графы.** LinkedIn, Lightcast, Textkernel, Sovren считают
   близость навыков на своих данных и не отдают числа открыто.
2. **Иерархия ≠ близость.** Два навыка с общим родителем (`PostgreSQL` и
   `MySQL` под `SQL`) могут быть ближе или дальше, чем соседи по группе; степень
   родства в справочниках не задана.
3. **Эмбеддинги без калибровки.** Косинус между названиями навыков не является
   вероятностью замены и на коротких строках (`Go`, `C`, `R`) почти бесполезен.
4. **Co-occurrence.** PMI/косинус по совместной встречаемости в вакансиях даёт
   числа, но требует корпуса и валидации; на демо-данных корпуса нет.

Поэтому предлагается: **класс родства → число** по таблице из
`rfc-scoring-model.md` (синоним / родитель / ребёнок / сосед / нет связи).
Справочник поставляет класс, код — число.

## 5. Русский язык

| Что доступно | Ограничение |
|---|---|
| Wikidata aliases (ru) | качество неровное, нужна вычитка |
| `pymorphy3` | морфология («кубернетесом» → «кубернетес»), не семантика |
| RuWordNet | общие синонимы, не профессиональная лексика |
| hh.ru `key_skills` | свободный текст, справочника нет |
| ESCO / O*NET / Lightcast | английский; маппинг через перевод теряет точность |

Фактический минимум после мержа ветки `feature/vacancy-skill-kinds`:

- 84 навыка и 105 алиасов в сиде; цель — 150–300 навыков из демо-вакансий;
- русские алиасы есть точечно (`питон`, `докер`, `микросервисы`), морфологии нет:
  «кубернетесом» точным совпадением не находится;
- языки программирования заведены руками, Linguist ещё не подключён;
- групп смежности нет — это P1 вместе с картой смежных навыков.

Что добавить дальше:

- Linguist для `js`/`JavaScript`, `ts`/`TypeScript` и семейств (`group`);
- синонимы Stack Overflow и Wikidata, вычитанные вручную;
- морфологию (`pymorphy3` или слой падежей на стороне Java) — решить, где;
- 20–30 групп смежности, заданных руками (`containers`, `queues`, `cloud`, `ml`,
  `frontend`, `databases`), а не выведенных из чужой похожести.

Полный каталог навыков пайплайну не нужен: сопоставление идёт против требований
конкретной вакансии и их алиасов (`rfc-feature-extraction.md` §6.2).

## 6. Формат данных

Предлагаемая структура записи (версионируется целиком):

```json
{
  "version": 1,
  "skills": [
    {
      "normalized_name": "kubernetes",
      "name": "Kubernetes",
      "aliases": ["k8s", "кубернетес", "кубер", "kubernetes cluster"],
      "group": "containers",
      "parents": ["container orchestration"],
      "source": ["esco", "wikidata", "linguist"],
      "reviewed": true
    }
  ],
  "groups": [
    { "name": "containers", "skills": ["kubernetes", "docker", "podman"] }
  ]
}
```

Текущая реализация хранит не JSON, а нормализованные строки: `skill` +
`skill_alias`. Формат выше — целевой для экспорта или для отдельного сервиса
справочника, а не описание существующих таблиц.

Соответствие контракту: `normalized_name` — то же поле, что в
`SkillRequirement.normalize_name` / `SkillPerResume.normalized_name`; расширение
`related_skills` в proto — отдельный вопрос (`rfc-feature-extraction.md` §9).

## 7. Способы поставки

| Вариант | Как работает | Плюсы | Минусы |
|---|---|---|---|
| **A. Пакет внутри `scoring-service`** | версионированный JSON в пакете, читается при старте | нет сетевых вызовов, детерминизм, просто | формально «сервис читает файл» — нужен ADR по `AGENTS.md` §13; словарь нельзя поправить без релиза Python |
| **B. Java передаёт в запросе** | нормализованные ключи и алиасы требований приходят в gRPC вместе с шаблоном | нет нового сервиса, владелец данных — Java (у неё `skill`/`skill_alias` в БД), Python остаётся stateless | раздувает запрос; для неявных навыков нужен словарь шире списка требований; правила сопоставления зависят от Java |
| **C. Отдельный gRPC-сервис справочника** | `scoring-service` (и другие) вызывает `LookupSkills` / `NormalizeSkill` | единый владелец данных, обновление без релиза потребителей, переиспользование в `vacancy-service` | новый сервис в `compose.yaml`; сетевой вызов на пути скоринга (латентность, таймауты, деградация); нужен новый контракт и версионирование; вопрос «кто владелец» |

### 7.1. Рекомендация с учётом реализованного

Нормализация уже написана в Java: `SkillCatalog` + `SkillNormalizer` + `skill_alias`
(ветка `feature/vacancy-skill-kinds`, после мержа). Значит «сервис справочника» —
это не новый код, а вынос существующего компонента за границу процесса. Отсюда
порядок:

1. **Сейчас — B.** Java передаёт в gRPC то, что уже умеет: `normalize_name`
   требования (посчитан `SkillNormalizer`) и, если нужно, снимок алиасов. Python
   не дублирует нормализацию и не читает файлов.
2. **Позже — C.** Когда появится причина (независимый релиз справочника, второй
   потребитель, админка), `SkillCatalog` становится gRPC-сервисом с методами
   `Normalize`, `Lookup`, `Related`. Контракт и версия словаря фиксируются тогда.
3. **A не рекомендуется.** Пакет внутри `scoring-service` дублирует данные,
   которые уже есть в БД, и нарушает правило «один владелец данных».

Причины, по которым C пока не оправдан: справочник крошечный и read-mostly,
отдельной команды-владельца нет, отдельного режима отказа тоже. Порог пересмотра
стоит записать в ADR: например, «нужен релиз справочника без релиза
`vacancy-service`» или «справочник стал отдельным сервисом с собственной
нагрузкой».

C и B не исключают друг друга: C удобен для наполнения и админки, B — для
горячего пути, потому что `scoring-service` stateless (`AGENTS.md` §5).

### 7.2. Схема и внешние ключи

Существующие таблицы лежат в `public` (миграции не указывают схему). Отдельная
схема `dictionary` — это не физическая изоляция: один инстанс, один WAL, один пул
соединений. Она даёт имена, права и возможность среза `pg_dump -n dictionary`.

Правила, которые сохраняют возможность выноса:

1. **Зависимость только в одну сторону:** бизнес-схемы ссылаются на справочник,
   обратных FK нет.
2. **`ON DELETE RESTRICT`** для `vacancy_requirement.skill_id` — уже так: удалить
   используемый навык нельзя. У `skill` нет `is_active`, поэтому «мягкое» удаление
   пока не предусмотрено — открытый вопрос. У `skill_alias` сейчас
   `ON DELETE CASCADE`: алиас не самостоятельная сущность.
3. **Снимок обязателен.** FK гарантирует, что `skill_id` существует сейчас, но не
   то, что он означал в момент создания версии шаблона. Переименование или слияние
   навыка молча меняет смысл старой версии. Снимок (`skill_id`,
   `normalized_name`, версия словаря) должен быть в версии шаблона и в запуске
   скоринга (`AGENTS.md` §4 инв. 13). Сейчас его нет — это открытый вопрос.
4. **`skill_kind_stat` — не справочник.** Это статистика использования
   (специализация × уровень × навык), поэтому в схеме `dictionary` ей не место.
5. **Никакого `search_path`** — только полные имена `dictionary.skill`.
6. **Миграции по каталогам** (`changes/dictionary/…`, `changes/vacancy/…`) с
   порядком «сначала справочник» — подготовка к выносу, а не преждевременная
   работа.

### Что нужно решить до реализации

1. Кто владелец сервиса справочника (сейчас — Java-модуль).
2. Контракт C: какие методы (`Normalize`, `Lookup`, `Related`, `Groups`), формат
   ответа, нужен ли батч.
3. Что именно Java передаёт в горячем пути: только `normalize_name` или ещё
   снимок алиасов для неявных навыков.
4. Деградация: при недоступности справочника скоринг продолжает работу по точному
   совпадению, а не падает.
5. Снимок версии шаблона: минимальный (`skill_id`, `normalized_name`, версия
   словаря) или расширенный (`aliases_hash`, `groups_hash`).
6. Переезд в схему `dictionary`: сейчас или отдельной миграцией перед выносом.

## 9. Открытые вопросы

1. Способ поставки: рекомендация «B сейчас / C позже» (раздел 7.1) требует
   решения команды и ADR.
2. Переезд в схему `dictionary` и снимок версии шаблона (раздел 7.2).
3. Достаточно ли 84 навыков в сиде для демо или нужен полный ESCO.
4. Морфология: `pymorphy3` в Python, слой на Java или ничего.
5. Использовать ли ESCOXLM-R как детерминированный экстрактор для A1 и как он
   покажет себя на русском.
6. Нужны ли `SFIA`-уровни для отчёта (не для скоринга).
7. Как обновляется курируемая часть: вручную, полуавтоматически из Wikidata или
   из наблюдений режима `shadow`.
8. Где проходит граница между «справочником» и «картой смежных навыков» из P1
   (`README.md` §13) — это один сервис или два.
