## Статус реализации v0

Формулы ниже остаются каноническим описанием модели и открытых вопросов. В коде
`scoring-service` реализована только часть; фактическое поведение нужно читать
вместе с этой таблицей.

| Элемент | Что реализовано в v0 | Что не реализовано |
|---|---|---|
| $S^{ij}$ | Детерминированно: навык — точный `skill_id`/ключ (`1.0`) или класс связи словаря (`0.5`); квалификация — бинарно; образование — `0.7·направление + 0.3·уровень`; опыт — сходство категории; текст — доля токенов | LLM-оценка сходства, эмбеддинги, гарантия $S=1$ для всех синонимов |
| $R_i$, $\mathtt{Rv}$ | Взвешенное покрытие и релевантность по `criticality` | Порог $T_\mathtt{Rv}$ и политика шорт-листа в `scoring-service` (политика живёт в Java) |
| $\tau_i$ | `0.5·(1+tanh(years/required−1)) · 2^(−recency/2)`, `A=B=1`, `T½=2` | Общий $\tau_\mathrm{total}$, извлечение `recency` из резюме, настройка `A/B/T½` по позиции |
| $t_i$ | Regex-эвристика: результат/метрика `0.8`, обязанность `0.5`, остальное `0.3` | Секционная классификация без ложных срабатываний на цифры |
| $\mathtt{Wv}^i$ | `OPTIONAL 0.25`, `NICE 0.5`, `REQUIRED 0.75`, `CRITICAL 1.0` | Формула из `weight`/`critical`; в scoring-контракте этих полей нет |
| $c_i$ | Для навыка `S·t·τ`, для опыта `S·τ`, для образования/текста `S`, для квалификации `1.0`; при $\lambda=0$ это эквивалентно $R_i'$ | Внешние $q_i^l$ и $\lambda_l$ |
| $\mathtt{Score}$ | Взвешенное покрытие; $F=0$, $\mathcal{M}=1$ | Формула $F$ и $\mathcal{F}>0$ |
| Границы | Подстановка граничных $\tau$ для навыков и опыта; для `NOT_STATED` верхняя граница `1.0` | Повторный расчёт всей модели и численный метод для немонотонных функций |
| Шкала | `0..1` внутри Python, `0..100` в API/БД | Округление и калибровка шкалы |
| Cap | Не применяется | Отдельный cap для критичных требований (по решению команды его нет) |

`scoring_weights` (`w_m`, `w_n`, `w_f`) остаётся в БД как совместимый артефакт
версии шаблона, но `scoring-service` эти поля не читает. `Wv` выводится из
`criticality`; `critical` в текущем API требований всегда `false`.

## Формализация требований
Для успешной сверки данных, представленных соискателем,
с требованиями вакансии, необходимы структурированные
данные и резюме, и вакансии. Их можно ввести в систему непосредственно
при размещении объявления о найме либо выделить из текстового
описания с помощью LLM. В любом случае, сперва необходимо
придумать подходящий формат данных.

### Общая информация о вакансии
* Уровень позиции: `intern`, `junior`, `middle`, `senior`.
* Требуемый стаж работы
* Категория работ: программист, преподаватель, инженер.

### Частные особенности вакансии/резюме

1. Класс фичи:
    * `Skill`
    * `Qualification`
    * `Education`
    * `Prior Experience`
    * `Unclassified`
2. Название фичи (выделяет конкретный экземпляр класса, однако не учитывает всей иерархии). Примеры:
    * `Skill`: `Rust`, `Podman`, `Chinese`.
    * `Education`: `Computer Science '24 at MIT`, `Bioengineering '28 at BSU`.
    * `Prior Experience`:
      > 2 years of Haskell development at Horns & Hooves JSC. Responsible for X, Y, Z.

      > Built a raytracing engine from scratch in Zig. Used callgrind for profiling,
      > boosting performance 4x. As a result, it renders Cornell box 7x faster than POV-Ray.
    * `Unclassified`: everything else (TODO: an example)
3. Свойства класса (структурированная информация об экземпляре,
которая используется для скоринга и/или принятия решения HR'ом)


| Класс              | Общие свойства | Свойства вакансии | Свойства резюме | Свойства синтеза |
|--------------------|----------------|-------------------|-----------------|------------------|
| `Skill`            | normalized name, tenure | - | recency | relevance, coverage, evidence  |
| `Qualification`    | canonical key, label | label | label | relevance, coverage, evidence |
| `Education`        | master, level         | - | university*, graduation year* | relevance, evidence |
| `Prior Experience` | tenure, category | - | dates, metrics, position | relevance, coverage |
| `Unclassified`     | plain text* | - | - | evidence |

*\*Помеченные свойства не могут использоваться при автоматическом скоринге*

В настоящий момент больше всего готова модель для оценивания навыков. Похожую модель
можно применить и оценки соответствия образования, добавляя соответствующим образом веса.
Под evidence понимается текстовое доказательство: дословная цитата из
входного текста резюме с границами.

Для образования уровень сравнивается не по числовым значениям protobuf-enum,
а по явному порядку:

```text
secondary < secondary_specialized < courses < bachelor < master < doctor
```

Курсы стоят между средней школой и бакалавриатом: они подтверждают среднее
образование, но не заменяют бакалавриат. Если требование — курсы, бакалавриат
считается достаточным; если требование — бакалавриат, курсы дают частичное
соответствие.

Квалификация — бинарный признак: `S^{ij} = 1` при совпадении канонических ключей
и `0` иначе; `t_i = 1`, `\tau_i = 1`, вес берётся из критичности требования.
Отсутствие квалификации даёт `NOT_STATED` с точкой `0` и верхней границей `1`.

### Отношения навыков

Словарь отдаёт класс связи, а не число `S^{ij}`. В v1 используются классы
`SAME_GROUP`, `RELATED`, `PARENT`, `CHILD`. Начальная политика `RelationPolicy`
в `scoring-service`:

| Класс | `S^{ij}` |
|---|---:|
| точное совпадение `skill_id` или ключа | 1.0 |
| `SAME_GROUP` | 0.7 |
| `RELATED` | 0.7 |
| `PARENT` | 0.6 |
| `CHILD` | 0.5 |
| нет связи | 0.0 |

Это стартовые значения для v1; они не меняют формулу `Score` и должны
уточняться по golden-тестам. Словарь не хранит эти числа.

### Версии навыков

Версия в имени навыка не создаёт новый навык. `scoring-service` отделяет
version tail и сравнивает базовые имена; правило живёт в
`src/api/scoring/versioning.py`.

Примеры:

- `Java` ↔ `Java 11/17` → база `Java`, `S = 1.0`;
- `Java 17` ↔ `Java 11/17` → версии пересекаются, `S = 1.0`;
- `C++17` ↔ `C++`, `C# 12` ↔ `C#`, `.NET 8` ↔ `.NET` → `S = 1.0`;
- `Java` ↔ `JavaScript`, `Java` ↔ `Java EE`, `Spring` ↔ `Spring Boot` →
  базы разные, `S = 0.0` или класс связи.

Version tail — это числовые версии и диапазоны (`11`, `11/17`, `11-17`,
`11+`, `1.8`) после пробела или разделителя, либо сразу после `+`/`#`
(`C++17`, `C#12`). Слова, меняющие смысл продукта (`EE`, `SE`, `Core`,
`Framework`, `Native`), не отрезаются.

Если версии есть с обеих сторон и не пересекаются, применяется
`VersionMatchPolicy`. Значение по умолчанию — `1.0`: v1 не штрафует за
несовпадение версий, чтобы не терять кандидатов. Политика заменяемая; изменение
её значения — изменение поведения `S`, поэтому фиксируется новой
`scoring_version` и golden-тестами.

Расширение будет произведено после реализации скоринга по навыкам. Данный раздел
больше приведен для документирования требуемых параметров от вакансии и облегчения
написания Protobuf.

## Ориентировочный пайплайн первичного скоринга
1. Получение структурированной информации о вакансии
2. Извлечение структурированной информации о резюме
3. Вычисление матрицы $S^{ij}$ и релевантностей $R_i, \mathtt{Rv}$.
4. Вычисление $\tau, \tau_i$.
5. Вычисление $t_i$ и $F$.
6. Вычисление $R_i'$ и $\mathtt{Score}$.
7. Повтор шагов 4-6 с граничными значениями для неточных данных и формирование вилки.
8. Фильтрация кандидатов на основе соответствия $R_i'$ критичных требований,
а также $\mathtt{Score}$ с выдачей рекомендации к направлению на проверку
внешних источников.

После проверки внешних источников применяется та же модель,
но она получает закэшированные данные там, где это применима
и обновляет оценки с учетом полученных сведений.

## Первичное определение

Пусть описание вакансии требует от кандидата навыков
$\mathtt{Sv}_i, i=\overline{1;n}$.
Каждому навыку присваивается **вес**
$\mathtt{Wv}^i \in [0;1]$.
Вес определяет важность навыка для данной вакансии.
Предполагается, что для необязательных навыков веса будут
меньше, чем для обязательных. Для удобства обозначим через
$T$ **пороговый уровень** для требований:
если $\tt{Wv}^i < T$, то навык считается необязательным.

В реализации v1 базовый вес зависит от критичности:
`OPTIONAL 0.25`, `NICE 0.5`, `REQUIRED 0.75`, `CRITICAL 1.0`.
`CriticalityWeightPolicy` получает распределение требований по критичности
и по умолчанию делит базовый вес на размер группы:

$$
\mathtt{Wv}^i = \frac{\mathrm{base}(criticality_i)}{\mathrm{count}(criticality_i)}
$$

Это сохраняет суммарный вес группы, но не даёт большой группе требований
доминировать только за счёт количества. Нормализацию можно отключить
(`normalize_by_counts=False`) или задать собственную формулу через `weight_fn`.
Пусть навыки отсортированы в порядке убывания, причем

$$
{\mathtt{Wv}}^1 \ge \mathtt{Wv}^2 \ge \dots \ge \mathtt{Wv}^t \ge T > \mathtt{Wv}^{t+1} \ge \dots \ge \mathtt{Wv}^n > 0
$$

Пусть после обработки текста резюме стало известно, что кандидат 
обладает навыками $\mathtt{Sr}_j, j=\overline{1;m}$.

Пусть $S^{ij} \in [0;1]$ - матрица схожести навыков из описания вакансии и резюме.
$S^{ij} = 1$, если два навыка целиком и полностью совпадают. $S^{ij}=0$,
если два навыка не имеют ничего общего (условно, язык FORTRAN и Elasticsearch,
хотя пример, возможно, не самый удачны).

Значение $S^{ij}$ можно получить различными способами (как с LLM, так
и с детерменистичными алгоритмами).
<details>
<summary>Один из вариантов (довольно дурацкий)</summary>
Каждый из сравниваемых навыков описывается одним словом,
после чего сравнивается близость эмбеддиногов по какой-либо норме.
</details>

**Релевантностью** резюме требованию вакансии $\mathtt{Sv}_i$ называется число
$R_i = \max\limits_j \mathtt{S}^{ij}$. То есть для каждого требования вакансии
учитывается наиболее подходящий навык.
*Примечание. Данная величина примерно соответствует* $m_r$ *из старой системы скоринга.*
> [!NOTE]
>
> Возможно, целесообразно также учитывать наличие схожих навыков.
> То есть $\mathtt{R}^\mathrm{Kafka}$ при наличии у кандидата Kafka и RabbitMQ
> выше, чем при наличии у него только Kafka. Но в таком случае $S^{ij}=1$
> утратит прежнее значение.

Наконец, **общая релевантность** резюме вакансии определяется как

$$ \mathtt{Rv} =
\frac{\sum\limits_i\mathtt{Wv}^iR_i}
{\sum\limits_i\mathtt{Wv}^i} \in [0;1] $$


Отметим, что общая релевантность показывает лишь наличие навыков,
необходимых для вакансии, однако не оценивает их качество.
Для нее можно установить пороговое значение $T_\mathtt{Rv}$ такое, что
при $\mathtt{Rv} < T_\mathtt{Rv}$ резюме считается не соответствующим
вакансии и не включается в шорт-лист.


## Более тонкий матчинг
### Стаж
Из данных резюме извлекается:
* Стаж в годах $E_i$ для каждого навыка и общий стаж работы
$E_\mathrm{общ}$.
* Для каждого навыка давность последнего использования $r_i$ в годах.

На основании этого получаем **темпоральный коэффициент**:

$$
\tau_i =
\frac{1}{2}\left[1 + \tanh\left({\mathcal{A}} \cdot\left(\frac{E_i}{E_\mathtt{треб,i}}-1\right)+{\mathcal{B}}\right)\right] \times \\
\times
{\LARGE 2}^{-\displaystyle\frac{r_i}{\mathcal{T_{1/2}}}}
$$

> #### Что делать, если $E_\mathrm{треб}$ равно нулю/неизвестно?
> Вероятно, в таком случае опыт нерелевантен. Можно принять $\tau = 1$,
> либо использовать формулу, которая незначительно увеличивает оценку за опыт.

> #### Что делать, если $E_j$ неизвестно?
> Вероятно, считать интервал от 0 до $E_\mathrm{треб}$.

Первый сомножитель отвечает за стаж, второй - за давность.

Гиперболический тангенс позволяет получить
незначительное преимущество тем, у кого опыта работы
больше, чем требуется, однако в то же время оставляет
шансы тем, у кого опыта немного меньше, но общая оценка
резюме хорошая. Данные допущения определяются
гиперпараметрами $\mathcal{A}$ и $\mathcal{B}$.
Предлагается референсное значение $\mathcal{A}=1, \mathcal{B}=1$.

Гиперпараметр $\mathcal{T_{1/2}}$ определяет скорость "угасания"
навыка и равен количеству лет, по прошествии которых оценка ухудшается
вдвое. Референс $\mathcal{T_{1/2}} = 2$.

> В текущей v1 recency отключён: $r_i = 0$, фактор свежести всегда равен `1`,
> а $\mathcal{T_{1/2}}$ в расчёте не участвует. Поле `recency` в контракте
> сохранено для будущей версии.

Темпоральный коэффициент общего стажа определяется аналогично:

$$
\tau =
% Часть 
\frac{1}{2}\left[1 + \tanh\left({\mathcal{A}} \cdot\left(\frac{E_\mathrm{общ}}{E_\mathtt{треб}}-1\right)+{\mathcal{B}}\right)\right]
$$

Параметры $\mathcal{A}, \mathcal{B}, \mathcal{T_{1/2}}$ можно подбирать в зависимости
от позиции и критичности требования.

### Убедительность заявления
Приоритет должен отдаваться тем навыкам, которые имеют более веское
подтверждение, чем просто перечисление.
Пока используем параметр $t_i$ из старой модели. Для каждого
навыка подтверждение классифицируется в одну из групп.
В зависимости от группы навыку присваивается вес:

| Группа | Вес |
|--------|-----|
| просто перечислен как навык | 0.5 |
| обязанность без деталей | 0.75 |
| действие с результатом или метрикой | 1.0 |
| как расширить модель? |


Если навык дополнительно найден в проверенной цитате описания опыта работы
или проекта, используется более сильная цитата:

$$
t_i = \max(t_i^{\text{навык}}, t_i^{\text{опыт}})
$$

Это не отдельное слагаемое `Score`, а уточнение убедительности уже найденного
навыка. Цитата из опыта должна быть подстрокой обезличенного текста и
упоминать тот же навык; иначе она не учитывается.

### Статусы соответствия

Статус требования не должен говорить «полностью закрыто», если `coverage`
низкий. Действует единое правило: статус `FULL` требует достаточного
покрытия, а не только точного названия признака.

| Тип | `FULL` | `PARTIAL` | `ABSENT` |
|---|---|---|---|
| `Skill` | `coverage >= SCORING_SERVICE_SKILL_FULL_COVERAGE` (по умолчанию `0.70`) и стаж достаточен | `relevance >= 0.50`, но не `FULL` | `relevance < 0.50` |
| `Prior Experience` | `coverage >= 0.85` и стаж достаточен | `relevance >= 0.50`, но не `FULL` | `relevance < 0.50` |
| `Education` | `coverage >= 0.85` | `coverage >= 0.50` | `coverage < 0.50` |
| `Text` | `coverage >= 0.75` | `coverage >= 0.35` | `coverage < 0.35` |
| `Qualification` | подтверждена | — | — |

Если проверенной цитаты нет, статус — `NOT_STATED`, а не `ABSENT`.
Недостаточный стаж имеет приоритет над порогом покрытия: статус остаётся
`PARTIAL` с `GAP_REASON_INSUFFICIENT_TENURE`.

Порог навыка ниже остальных, потому что навык может быть подтверждён
только перечислением (`t_i = 0.5`). Порог навыка задаётся конфигурацией
`SCORING_SERVICE_SKILL_FULL_COVERAGE`.

### Соответствие опыта соискателя
Необходимо отдавать преимущество тем кандидатам, у которых уже
есть опыт в той сфере, куда мы их нанимаем (учтено в параметра $F$
из старой модели, однако способ вычисления не разработан).
Поскольку в новой модели стаж сверх требований учитывается отдельно,
а уровень задается косвенно при подборе гиперпараметров, в новой модели
через $F$ мы обозначим именно соответствие домена.

Проверить соответствие домена можно на основе указанного в резюме
опыта работы и проектов, а также профиля на GitHub.

## Финализация
Для каждого требования вакансии мы определили релевантность
резюме. У нас также есть общая релевантность.

Теперь релевантность необходимо связать с убедительностью и темпоральным
фактором.
В предыдущей версии итоговый вес для навыка (покрытие)
считался как 

$$ c_r = \left(1 - (1-q_r)\prod(1-\lambda q_{r,l})\right) \cdot D, $$

где $q \propto mtp$, а $D$ задает стаж с капом. Стаж сверх требований
учитывается отдельно.

В нашей версии $m$ соответствует $R_i$, а стаж учтен в 
темпоральном факторе каждого из
навыков (по мере возможности) и в совокупности. Стаж
сверх требований также учитывается в $\tau$.
Поэтому примем пока

$$ c_i = 1 - (1-R_i')\prod_l(1-\lambda_lq^l_i) $$

|переменная| пояснение |
|--|--|
| $q^l_i \in [0;1]$ | коэффициент для внешнего источника $l$ |
| $\;\lambda_l \in [0;1]$ | поправочный коэффициент с учетом позиции |
|$ R_i' $ | $R_i' = R_it_i\tau_i$ |


С этим введем понятие уточненной релевантности резюме:

$$ R' = \frac{\sum_i c_i\mathtt{Wv}^i}{\sum_i \mathtt{Wv}^i} $$

Тогда итоговая оценка вычисляется по формуле:

$$
\mathtt{Score} = \mathcal{M}\cdot R' + \mathcal{F} \cdot F + \mathcal{T}\cdot T_\mathrm{total}
\qquad \mathcal{M},\,\mathcal{F},\,\mathcal{T}\;\in[0; 1],\;
\mathcal{M}+\mathcal{F}+\mathcal{T}=1
$$

где $T_\mathrm{total}$ — соответствие общего стажа резюме требуемому стажу
вакансии:

$$
T_\mathrm{total} =
\frac{1}{2}\left[1 + \tanh\left(
\mathcal{A}\cdot\left(\frac{E_\mathrm{общ}}{E_\mathrm{req}} - 1\right) + \mathcal{B}
\right)\right]
$$

При $E_\mathrm{req}=0$ слагаемое стажа отключено: $\mathcal{T}=0$, чтобы
кандидат не получал вклад за отсутствующее требование. Неизвестный
$E_\mathrm{общ}$ даёт вилку по тем же правилам, что и $\tau_i$.
Значение $\mathcal{T}$ настраивается в `scoring-service`
(`SCORING_SERVICE_TENURE_WEIGHT`, по умолчанию `0.1`) и должно фиксироваться
в `scoring_version`/параметрах запуска.

*Замечание. Поскольку получить часть сведений невозможно,
оценку необходимо провести несколько раз с граничными значениями
(либо использовать численный метод, если функции немонотонны), чтобы получить
наибольшее и наименьшее значения *

## О задании весов $\mathtt{Wv}^i$ и учете приоритета требований
Веса не являются частью публичного API и должны задаваться таким образом, чтобы приоритет отдавался
критичным навыкам без введения явных капов.
Условно (todo),

$$ \mathtt{Wv}^i \propto \exp\left(\mathcal{D}\cdot\left(\mathtt{dbWeight}_{i} \in\overline{1;3} + \mathcal{C}\cdot\mathtt{dbCrit_{i}}\right)\right) $$

Кроме того, для придания приоритета различным требованиям можно использовать нелинейные активаторы,
которые будут содержать внутри себя ограничения.

## Выходные данные модели
### Предварительная оценка
Предварительная оценка производится на основании текста 
резюме, из которого извлекаются структурированные данные,
а также структурированного описания вакансии.

| Величина         | Значение                |
|------------------|-------------------------|
| **Скаляры**                                |
| $\mathtt{Rv}$         | Соответствие наборов навыков|
| $\mathtt{Score}_l$    | Нижняя граница оценки |
| $\mathtt{Score}_h$    | Верхняя граница оценки |
| $\mathtt{Score}$      | Оценка на основании резюме и предопределенных значений для неизвестных параметров |
| $\mathtt{Tenure}: \mathtt{int?}$ | Общий стаж в годах |
| $\mathtt{refine: bool}$ | Необходимость привлечения внешних источников для уточнения оценки |
| **По навыкам** $\mathtt{Sv}_i$  из вакансии                              |
| $c_i$        | Покрытие навыка         |
| $\mathtt{RecUnk}_i: \mathtt{bool}$   | Флаг неизвестности давности |
| $\mathtt{Tenure}_i: \mathtt{int?}$   | Стаж в годах или неизвестность |
| $\mathtt{evidence}_i: \mathtt{FeatureEvidence?}$ | Доказательство навыка: цитата из файла и поддиапазон, откуда она взята |

Примечание. После некоторых полей указан тип данных. Вопросительный
знак в таком случае означает, что данные могут принимать значение `null`.
Если тип не указан, подразумевается число с плавающей точкой (вероятнее всего, `double`).

### Окончательная оценка
Окончательная оценка учитывает данные из внешних источников.
