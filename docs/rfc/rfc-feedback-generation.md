# RFC: детерминированная генерация объяснений

> [!NOTE]
> Документ описывает **слой объяснений**, а не математику скоринга. Формулы
> `S^{ij}`, `R_i`, `R_i'`, `c_i`, `Score`, `Score_l`, `Score_h` и правило
> `Score_pre`/`Score_final` не меняются. Генерация не вызывает LLM и не
> добавляет новых RPC.

## 1. Контекст

`TASK.md` требует для каждой вакансии показать сильные стороны кандидата,
пробелы и риски, вопросы кандидату и рекомендации для дальнейшей коммуникации.
Контракт `EvaluateResumeMatchResponse` уже содержит поля `strengths`, `gaps`,
`risks`, `questions`, `recruiter_note`.

До этого изменения `scoring-service/src/api/scoring/evaluator.py` заполнял их
заглушками:

- `strengths` — только `label` требований со статусом `CORRESPONDENCE_FULL`;
- `risks` — только аномалии дат и пустые секции резюме;
- `questions` — четыре общих вопроса по `gap_reason`;
- `recruiter_note` — счётчики покрытия без рекомендации следующего шага.

При этом `EvaluateResumeMatch` и `EvaluateResumeMatches` по инварианту 10 не
вызывают LLM: это закреплено тестом
`test_evaluate_resume_match_does_not_call_llm`. Поэтому генерация объяснений
должна быть детерминированной и опираться только на уже посчитанные факты.

## 2. Решение

В `scoring-service` добавляется модуль `src/api/scoring/feedback.py`:

```text
EvaluateResumeMatch
        │
        ├─ RequirementMatcher ──► RequirementScore
        ├─ ScoringCalculator  ──► GeneralScore
        │
        └─ FeedbackBuilder
               ├─ FeedbackFact   (что сказать: тип, условие, приоритет, слоты)
               ├─ FeedbackTemplate (как сказать: текст с слотами)
               └─ Feedback        (strengths, risks, questions, recruiter_note)
```

`FeedbackBuilder` получает:

- `ParsedResume` — структурированные навыки, образование и опыт;
- `Vacancy` — тип требования, критичность и требуемый стаж;
- `matches` — результаты сопоставления `RequirementScore`;
- `GeneralScore` — `Score`, `Score_l`, `Score_h`;
- `reference_date` — дата, на которую считается стаж;
- `total_years` — суммарный стаж, уже посчитанный в `ResumeEvaluator`.

Модуль не меняет `matches`, `gaps` и `GeneralScore`. Он только формирует текст
объяснений. `gaps` остаётся структурированным списком `Gap { requirement_id,
reason }`, как в контракте. Отдельного поля `weaknesses` в v1 нет.

## 3. Входные данные и границы

| Данные | Откуда | Использование |
|---|---|---|
| `resume.skills`, `resume.education`, `resume.experience` | `ParsedResume` | Риски качества данных, даты, завышенный стаж |
| `vacancy.requirements` | `Vacancy` | Тип требования, критичность, требуемый стаж |
| `status`, `gap_reason`, `coverage`, `years_found`, `evidence`, `label` | `RequirementScore` | Сильные стороны, пробелы, риски, вопросы |
| `score`, `score_low`, `score_high` | `GeneralScore` | Вступление рекомендации рекрутёру |
| `reference_date` | запрос | Проверка будущих дат и расчёт стажа |
| `total_years` | `total_experience_years` | Проверка завышенного стажа навыка |

`RequirementScore` не хранит само требование, поэтому тип и требуемый стаж
берутся из `Vacancy.requirements[requirement_id]`. Если требование отсутствует
(например, пакетный вызов с рассогласованным шаблоном), используется
`resume_kind` из `RequirementScore`, а требуемый стаж считается неизвестным.

Границы:

- `scoring-service` остаётся stateless: нет БД, файлов, hh, GitHub и PII;
- LLM не вызывается;
- формулы скоринга не дублируются и не меняются;
- генерация не решает, кого пригласить или отклонить.

## 4. Правила отбора фактов

### 4.1. Сильные стороны

Берутся только требования со статусом `CORRESPONDENCE_FULL`.

- Обязательно наличие проверенной цитаты `match.evidence`. Если цитаты нет,
  сильная сторона не создаётся: неподтверждённое утверждение не считается
  доказательством.
- Сортировка: сначала критичность (`CRITICAL` → `REQUIRED` → `NICE` →
  `OPTIONAL`), затем покрытие, затем `requirement_id`.
- Для `CRITICAL` используется шаблон `strength.critical_full`.
- Для остальных — шаблон по типу требования: `skill`, `experience`,
  `education`, `text`.
- Для навыка и опыта добавляется `tenure_note`, если требуемый стаж больше нуля
  и найденный стаж известен: «Найденный стаж — 3 года, требуется 3 года».
- Лимит — 5 сильных сторон.

### 4.2. Пробелы

Пробелы не генерируются заново. `gaps` собирается в `ResumeEvaluator` из
`RequirementScore.gap_reason` и остаётся без изменений:

```text
Gap { requirement_id, reason }
```

Текст пробела для UI берётся из `matches[requirement_id].comment` и
`matches[requirement_id].evidence`, как и раньше. Отдельный список `weaknesses`
в v1 не вводится: пробелы и частичные соответствия уже видны в `gaps` и
`matches`. Это решение можно пересмотреть, когда UI потребует отдельную
секцию «слабые стороны».

### 4.3. Риски

Риски строятся по следующим правилам:

| Условие | Приоритет | Что попадает в текст |
|---|---:|---|
| Критичное требование не `FULL` (кроме `INSUFFICIENT_TENURE`) | 100 | «Критичное требование «X» не подтверждено / подтверждено частично» |
| Обязательное требование не `FULL` (кроме `INSUFFICIENT_TENURE`) | 80 | «Обязательное требование «X» не закрыто полностью: …» |
| `INSUFFICIENT_TENURE` | 110 / 90 / 60 / 40 | «Подтверждён стаж 1 год, а требуется 3 года» |
| Противоречие дат: начало позже даты оценки или конец раньше начала | 90 | «В датах опыта есть пробел или расхождение: …» |
| Завышенный стаж навыка: `skill.tenure > total_years + 1` | 60 | «Заявленный стаж по навыку «X» (10 лет) превышает общий стаж (2 года)» |
| Не указано начало периода опыта | 55 | «В датах опыта есть пробел: не указано начало периода» |
| Нет релевантного раздела резюме | 40 | «В резюме нет раздела «навыки/опыт работы/образование»» |
| Доля `NOT_STATED` ≥ 40% при ≥ 2 требованиях | 30 | «Доля требований без сведений — 2 из 5; вилка оценки широкая» |

Приоритет `INSUFFICIENT_TENURE` зависит от критичности: `CRITICAL` — 110,
`REQUIRED` — 90, `NICE` — 60, `OPTIONAL` — 40. Это на 10 выше базового
приоритета критичности, потому что недостаточный стаж — конкретный проверяемый
факт, а не общий пробел.

Особенности:

- `INSUFFICIENT_TENURE` не дублируется как `critical_gap` или `required_gap`:
  для него есть отдельный шаблон с найденным и требуемым стажем.
- Для `critical_gap` используется `status_phrase`: «в резюме не подтверждено»
  для `NOT_STATED`, «не подтверждено» для `ABSENT` и «подтверждено частично»
  для `PARTIAL`. Формулировка «не подтверждено» не применяется к частичному
  соответствию.
- `missing_data` добавляется только для тех секций, которые действительно
  нужны вакансии: если в вакансии нет требований к образованию, отсутствие
  образования в резюме не считается риском.
- Даты проверяются по `reference_date`; компания и должность в текст не
  попадают.
- Лимит — 5 рисков.

### 4.4. Вопросы

Вопросы строятся по интентам, а не по общим фразам «есть ли опыт?».

| Тип требования | Статус / причина | Шаблон |
|---|---|---|
| `skill` | `NOT_STATED` | `question.skill_not_stated` |
| `qualification` | `NOT_STATED` | `question.qualification_not_stated` |
| `experience` | `NOT_STATED` | `question.experience_not_stated` |
| `education` | `NOT_STATED` | `question.education_not_stated` |
| `text` | `NOT_STATED` | `question.text_not_stated` |
| `skill` | `INSUFFICIENT_TENURE` | `question.skill_insufficient_tenure` |
| `experience` | `INSUFFICIENT_TENURE` | `question.experience_insufficient_tenure` |
| любое | `PARTIAL` | `question.partial` |
| любое | `ABSENT` | `question.absent` |
| опыт | противоречие дат | `question.date_issue` |

Правила:

- Сортировка: критичность, затем бонус за причину пробела
  (`INSUFFICIENT_TENURE` +10, `ABSENT` +5), затем `requirement_id`.
- Лимит — 5 вопросов.
- Для `NOT_STATED` используются только формулировки «в резюме не указан
  навык», «в резюме не указан опыт», «в резюме не указано образование»,
  «в резюме не указано подтверждение требования». Запрещены «не знает»,
  «не владеет», «нет навыка», «слабый».
- Для `ABSENT` подчёркивается, что в резюме есть близкий опыт, но требование
  не подтверждено; вопрос спрашивает о похожих инструментах и задачах.
- Для `INSUFFICIENT_TENURE` в вопросе есть найденный и требуемый стаж.
- Для противоречия дат вопрос просит уточнить фактические периоды работы;
  приоритет такого вопроса — 95, при отсутствии начала периода — 50.

### 4.5. Рекомендация рекрутёру

`recruiter_note` состоит из двух частей: вступление и следующий шаг.

Вступление выбирается по `GeneralScore.score`:

| Диапазон | Шаблон |
|---|---|
| `score >= 0.75` | `note.opener_high` |
| `0.45 <= score < 0.75` | `note.opener_mid` |
| `score < 0.45` | `note.opener_low` |

Следующий шаг:

- если есть важные пробелы (`CRITICAL`, `REQUIRED` или
  `INSUFFICIENT_TENURE`) — `note.next_clarify` с топ-3 темами;
- иначе если `score >= 0.75` — `note.next_interview`;
- иначе — `note.next_review`.

Ограничения:

- итоговый текст — не длиннее 500 символов; если не помещается, остаётся
  только вступление;
- рекомендация не содержит автоматического «пригласить» или «отказать»;
- при отсутствии требований — `fallback.no_requirements`;
- если структурированных данных нет и все требования `NOT_STATED` —
  `fallback.no_data`.

## 5. Приоритеты и лимиты

Приоритеты — это политика отображения, а не часть формулы скоринга. Они не
входят в `Score` и не меняют `Wv`, `c_i` или границы.

| Критичность | Базовый приоритет |
|---|---:|
| `CRITICAL` | 100 |
| `REQUIRED` | 80 |
| `NICE` | 50 |
| `OPTIONAL` | 30 |
| `UNSPECIFIED` | 40 |

| Параметр | Значение |
|---|---:|
| Сильные стороны | 5 |
| Риски | 5 |
| Вопросы | 5 |
| Длина одного текста | 400 символов |
| Длина `recruiter_note` | 500 символов |
| Длина названия требования | 120 символов |
| Длина цитаты | 160 символов |

Сортировка фактов: `(-priority, fact_id)`. Это гарантирует, что при одинаковом
приоритете порядок не зависит от порядка словаря или protobuf-map.

## 7. Слоты и форматирование

| Слот | Значение |
|---|---|
| `{label}` | Название требования; пробелы схлопнуты, длина ≤ 120 символов |
| `{evidence}` | Фрагмент проверенной цитаты из `match.evidence`; пробелы схлопнуты, длина ≤ 160 символов, многоточие не добавляется |
| `{tenure_note}` | Пустая строка или « Найденный стаж — 3 года, требуется 3 года.» |
| `{found_years}`, `{required_years}`, `{total_years}` | Стаж в годах с русским склонением |
| `{status_phrase}` | «в резюме не подтверждено», «не подтверждено» или «подтверждено частично» |
| `{status_note}` | «в резюме нет сведений», «подтверждения в резюме нет», «подтверждение частичное» |
| `{detail}` | Описание проблемы дат без компании и должности |
| `{section}` | «навыки», «опыт работы», «образование» |
| `{top_topics}` | До трёх тем для уточнения: навык «Kafka», опыт в категории «backend» |
| `{score}`, `{score_low}`, `{score_high}` | Проценты, например `47%` |
| `{full_count}`, `{total_count}`, `{not_stated_count}` | Целые числа |

Правила форматирования:

- стаж: `1 год`, `2 года`, `5 лет`, `21 год`, `1,5 года`; меньше года —
  «менее года»;
- длинная цитата обрезается по границе слова до 160 символов; многоточие не
  добавляется, чтобы фрагмент оставался подстрокой проверенной цитаты;
- названия требований не склоняются: «по требованию «X»», «навык «X»»,
  «опыт в категории «X»», «образование по направлению «X»»;
- тон нейтрально-профессиональный; запрещены «слабый», «не знает»,
  «не владеет», «отказ», «пригласить»;
- если после подстановки остались `{` или `}`, шаблон считается невалидным;
- если текст длиннее 400 символов, факт пропускается;
- если слота не хватает, пробуются следующие варианты условия; если все
  невалидны, факт пропускается.

## 8. Детерминированный выбор и дедупликация

1. Факты сортируются по `(-priority, fact_id)`.
2. Для условия с `N` шаблонами индекс выбирается как
   `int(sha256(fact_id)[:8], "big") % N`.
3. Если выбранный шаблон не рендерится (нет слота, остались скобки, слишком
   длинный текст), проверяются следующие варианты в стабильном порядке.
4. Одинаковые отрендеренные тексты удаляются.
5. После дедупликации применяется лимит группы.

Свойства:

- один и тот же вход даёт один и тот же набор текстов;
- нет случайности, времени и обращений к LLM;
- порядок не зависит от порядка `dict` или protobuf-map;
- добавление нового варианта шаблона не меняет уже выбранные тексты, если
  `fact_id` и количество вариантов остаются прежними.

## 9. Маппинг в контракт

| Факт | Поле `EvaluateResumeMatchResponse` |
|---|---|
| `strength` | `strengths` |
| `gap` | `gaps` (без изменений) |
| `risk` | `risks` |
| `question` | `questions` |
| `note` | `recruiter_note` |
| `fallback` | `recruiter_note` |

Контракт не меняется: новых полей и RPC нет. `gaps` остаётся
структурированным, `matches[requirement_id]` хранит цитату, комментарий и
найденный стаж.

Версия каталога `feedback-templates.v2` пока не входит в контракт. Она
пишется в лог `evaluate resume match` как `feedback=feedback-templates.v2`.
Чтобы версия сохранялась в неизменяемом запуске скоринга, нужно добавить поле
в `EvaluateResumeMatchResponse` и в `score_run`; это отдельное изменение
контракта.

## 10. Логирование и приватность

- LLM не вызывается, новых внешних вызовов нет.
- В лог пишутся только метаданные: количество требований, совпадений,
  пробелов, сильных сторон, рисков и вопросов, версия каталога.
- Тексты резюме, цитаты, названия требований и сгенерированные тексты в лог не
  попадают.
- Цитаты в ответе берутся только из уже проверенного `match.evidence`; новых
  цитат генератор не создаёт.
- Сервис остаётся stateless и не получает PII: на вход приходит обезличенный
  текст, маскировка выполняется в Java до вызова `scoring-service`.

Пример события:

```text
evaluate resume match requirements=5 matches=5 gaps=2 strengths=3 risks=2 questions=2 feedback=feedback-templates.v2
```

## 12. Открытые вопросы

1. **Версия каталога в контракте.** Сейчас `feedback-templates.v2` есть только
   в коде и логах. Для воспроизводимости сохранённых запусков нужно поле в
   `EvaluateResumeMatchResponse` и `score_run`.
2. **Отображение в UI.** `ReportService`, OpenAPI и `ReportView.vue` пока не
   отдают `strengths`, `risks`, `questions`, `recruiter_note`. Это отдельная
   задача Java/frontend.
3. **Отдельные слабые стороны.** В v1 их нет: пробелы и частичные
   соответствия остаются в `gaps` и `matches`. Если UI потребует отдельную
   секцию, добавим `weaknesses` отдельным изменением контракта.
4. **Источник требования.** `RequirementSource` (`REQUIREMENT`/`DUTY`) в v1 не
   используется: все формулировки говорят «требование». Если понадобится
   различать требования и обязанности, добавим слот `source_label`.
5. **Локализация.** Каталог v1 — русский. Для других языков понадобится
   отдельный каталог и версия.
6. **Доменные follow-up вопросы.** Детерминированный слой не строит глубокие
   вопросы по конкретной технологии; это задача будущего LLM-перефразировщика
   или расширения каталога.
7. **Разнообразие формулировок.** В v1 большинство условий имеет один вариант.
   Если тексты окажутся слишком однообразными, добавим варианты и сохраним
   детерминированный выбор по `fact_id`.
