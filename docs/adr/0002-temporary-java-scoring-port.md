# ADR 0002. Временный локальный порт скоринга в Java

- **Статус:** принято, временно
- **Дата:** 2026-11-10
- **Контекст:** `resume-service`, инварианты 1, 4 и 6 (AGENTS.md, раздел 4)

## Контекст

По архитектуре арифметика скоринга живёт только в Python `scoring-service`, а Java
вызывает её по gRPC. Контракт `contracts/ml-internal.proto` ещё не реализован, а
сквозной сценарий «загрузка → Score_pre → шорт-лист → GitHub → Score_final → рейтинг»
нужен уже сейчас. Без него нельзя проверить ни хранение запусков, ни отчёт, ни
слепой режим.

## Решение

В `resume-service` введён порт `ScoringClient` и два слоя:

- `LocalScoringClient` — детерминированный адаптер для MVP. Он не вызывает LLM:
  находит навык в обезличенном тексте, берёт предложение как цитату, эвристически
  оценивает `m` и `t`, считает `q`, `E`, `D`, `c_r`, `M`, `N`, `F`, cap и вилку.
- `ScoreCalculator` — временная Java-копия формул из README. Внутри нет времени и
  случайности: «сегодня» передаётся параметром.

Версия адаптера — `local-heuristic-v1`. Она записывается в `score_run.model_version`,
чтобы запуски оставались неизменяемыми и отличимыми от будущих gRPC-запусков.

Это осознанное временное нарушение правила «математика только в Python». Оно
зафиксировано здесь и должно быть снято, когда появится реальный контракт.

## Что проверяют тесты

- один и тот же вход даёт один и тот же балл;
- каждая цитата — подстрока обезличенного текста, иначе она отбрасывается;
- отсутствие GitHub не уменьшает балл;
- критичное требование с `c_r < 0.2` включает cap и метку;
- вилка всегда содержит итоговый балл.

## Последствия

- `LocalScoringClient` нельзя выдавать за настоящий `scoring-service`: его `m/t`
  эвристические, а не LLM-категории.
- При появлении `contracts/ml-internal.proto` адаптер заменяется gRPC-клиентом,
  `ScoreCalculator` удаляется, а golden-тесты переносятся в Python.
- Пока адаптер включён, README и отчёт должны явно говорить, что это MVP-заглушка,
  а не финальная модель.
