# ADR 0007: интеграция с hh.ru через публикацию и вебхуки

- **Статус:** принято
- **Дата:** 2026-11-13

## Контекст

Нужно, чтобы отклик на вакансию, опубликованную на hh.ru, автоматически попадал в наш сервис и
считался по шаблону именно этой вакансии. У нас уже есть режим «кандидаты под вакансию», но он
запускается вручную через загрузку файла. Нужен внешний вход и однозначное сопоставление вакансий.

## Решение

1. **Публикуем вакансию через HH API.** HR подтверждает шаблон, после чего платформа создаёт
   черновик `POST /vacancies/drafts`, публикует его `POST /vacancies/drafts/{id}/publish` и
   сохраняет `hh_vacancy_id`. Повторный запуск использует сохранённый `hh_draft_id` и не создаёт
   дубль.
2. **Сопоставляем по `hh_vacancy_id`, а не по названию.** Вебхук `NEW_NEGOTIATION_VACANCY`
   содержит `vacancy_id`, `resume_id`, `topic_id`. Привязка хранится в `vacancy_hh_publication`.
   Название, URL и текст вакансии не используются как ключ: они меняются и могут совпадать.
3. **Несвязанная вакансия — это inbox, а не автосоздание.** Событие сохраняется в
   `hh_webhook_event` со статусом `UNMATCHED`, HR получает алерт. Скоринг не запускается, пока
   вакансия не привязана.
4. **Отдельный одиночный пайплайн.** Отклик проходит маскировку, разбор и `Score_pre` против одной
   вакансии. `ScreeningService`, `DecideScreening` и top-N не вызываются: для одного кандидата
   top-N дал бы ложный шорт-лист. `screening_decision` остаётся пустым, решение принимает человек.
5. **`Score_final` не считаем.** В текущем сценарии внешние источники не привлекаются, GitHub
   отключён, `consentGithub=false`. В UI и Telegram явно подписано «предварительный скор».
6. **Telegram без PII.** Сообщение содержит название вакансии, `Score_pre` без вилки и ссылку
   на анализ (`/applications/{id}/report?phase=PRELIMINARY`). Имя, контакты и текст резюме
   не передаются. Доставка идёт через `notification_outbox` с дедупликацией и retry.
7. **hh-резюме минимизируем.** В текст для скоринга переносятся только профессиональные факты:
   должность, навыки, опыт, образование, языки. Имя, контакты, пол, возраст, фото и гражданство
   не переносятся.

## Последствия

- Появляются таблицы `vacancy_hh_publication`, `hh_subscription`, `hh_webhook_event`,
  `notification_outbox` и поля `source`/`external_ref` у отклика, кандидата и резюме.
- Публикация на hh зависит от токена работодателя и полноты маппинга полей. В MVP маппинг
  минимальный: title, description, area, experience, employment_form, schedule,
  professional_roles из конфигурации. Для реального hh потребуется уточнить справочники.
- Вебхук hh не подписывает запросы. Защита — секрет в query-параметре, проверка `subscription_id`
  и, при необходимости, `employer_id`. Секрет не логируется.
- Если hh вернул `403` на резюме, это ожидаемая деградация: событие получает `FAILED`, HR видит
  алерт, остальные отклики продолжают обрабатываться.
- Старые запуски не пересчитываются. Новый шаблон вакансии влияет только на новые отклики.

## Открытые вопросы

- Полный маппинг специализаций и уровней на справочники hh (professional_roles, area,
  experience, employment_form).
- Нужен ли HR ручной fallback-привязки для вакансий, опубликованных вне платформы.
- Нужен ли второй алерт после ручного батч-скрининга с `Score_final`.
