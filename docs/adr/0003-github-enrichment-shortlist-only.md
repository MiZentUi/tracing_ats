# ADR 0003. GitHub только для шорт-листа и только по согласию

- **Статус:** принято
- **Дата:** 2026-11-10
- **Контекст:** `resume-service`, инварианты 3 и 8 (AGENTS.md, раздел 4)

## Контекст

GitHub может подтвердить навык, но не должен превращаться в обязательное условие.
Многие сильные кандидаты не публикуют код, а GitHub API ограничен по rate limit.
Скрапинг всех откликов нарушает и приватность, и лимиты.

## Решение

1. Предварительный `Score_pre` считается по обезличенному тексту для всех резюме.
2. `vacancy-service` применяет политику шорт-листа ко всей пачке и возвращает
   `SHORTLISTED`, `BORDERLINE` или `NOT_SHORTLISTED`.
3. GitHub вызывается только если одновременно:
   - решение `SHORTLISTED`;
   - кандидат дал согласие (`consent_github=true` при загрузке);
   - в зашифрованном vault есть GitHub-ссылка.
4. `GitHubEnricher` считает `q_gh` по конкретному навыку, а не «общий балл GitHub»:

   ```text
   q_gh(X) = A · (0.5·V + 0.3·S + 0.2·K) · ρ
   ```

   `A` — авторство (в MVP 1 для собственных не-форков), `V` — объём кода,
   `S` — стабильность, `K` — культура проекта (тесты, CI, README), `ρ` — свежесть.
5. Признаки накрутки (например, массовая загрузка репозитория) умножают `q_gh` на 0.5
   и добавляют флаг, но не блокируют кандидата.
6. Отсутствие GitHub, ошибка API или пустой профиль дают пустой набор доказательств.
   `q_ext = 0`, балл не уменьшается.
7. Факты по каждому навыку сохраняются в `external_evidence`; сырые ответы API и
   логин кандидата в логи не попадают.

## Последствия

- `Score_final` для не-шорт-листа равен `Score_pre` по фактам, но это отдельный
  неизменяемый запуск с подписью «итоговый».
- Включение GitHub — конфигурационный флаг `ATS_GITHUB_ENABLED`; токен не
  обязателен для MVP, но без него действует низкий лимит анонимных запросов.
  Ошибки и превышение лимита не роняют пакет.
- Ошибка GitHub не роняет пакет: кандидат остаётся в рейтинге с текстовыми
  доказательствами.
