# ADR 0007. UI-этап: приоритет TASK.md и только факты из отчёта

- **Статус:** принято
- **Дата:** 2026-11-14
- **Контекст:** `TASK.md`, `AGENTS.md`, текущая ветка `feature/ui-feedback`

## Контекст

Команда уточнила границы текущего UI-этапа:

- приоритет — требования `TASK.md`, а не полный бэклог README;
- GitHub-обогащение в этом этапе не развивается и в UI не выводится;
- финальная математическая модель скоринга не зафиксирована;
- импорт с HH ведётся в отдельной ветке;
- под отчётом понимается HTML-страница отчёта, PDF-выгрузка не входит в этап.

При этом в `TASK.md` остаются требования, которые уже обеспечены данными
backend, но ещё не полностью отражены в UI.

## Решение

1. UI показывает только факты, статусы, цитаты и длительность, но не раскрывает
   внутренние коэффициенты и формулы скоринга. Вилку `scoreLow`/`scoreHigh`
   продолжаем не показывать.
2. В текущий пакет входят:
   - карточка извлечённого опыта на странице резюме;
   - колонка подтверждённого стажа в HTML-отчёте;
   - легенда статусов отчёта, явно разделяющая «не указано» и «отсутствует».
3. GitHub-доказательства, веса `λ`/`wM`/`wN`/`wF`, профили junior/senior,
   импорт с HH и PDF-отчёт не добавляются в этот этап.
4. Значения для отчёта берутся из уже сохранённого результата скоринга:
   `RequirementReportItem.tenure`, `status`, `evidenceQuote`, `gap`.
   Новых вычислений в UI нет.

## Последствия

- `GET /api/v1/resumes/{resumeId}/extraction` расширяется опытом из
  `ParsedResume.experience`; PII не раскрывается, используется обезличенный текст.
- HTML-отчёт становится понятнее без привязки к финальной формуле скоринга.
- Если позже появятся GitHub или финальные веса, их нужно добавлять отдельным
  контрактным изменением и отдельным ADR, а не достраивать текущий UI.
- ADR 0003 остаётся историей backend-решения; в текущем UI-этапе GitHub не
  отображается и не развивается.
